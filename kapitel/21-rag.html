RAG: Vektorstores & Q&A über eigene Daten

In diesem Kapitel baust du ein kleines Frage-Antwort-System über eigene Dokumente. Die Technik dahinter heißt RAG, kurz für Retrieval-Augmented Generation. Auf Deutsch: erst nachschlagen, dann antworten. Der Unterschied zu Memory aus Kapitel 20: Memory merkt sich ein Gespräch. RAG sucht in einem Wissensbestand. Das ist eine andere Aufgabe und braucht eine andere Kontrolle.

ca. 45 Minuten Niveau: Fortgeschrittene Grundlagen Voraussetzung: Kapitel 6, 9, 12, 20

Was du brauchst

  • Eine n8n-Instanz mit den AI-/LangChain-Nodes.
  • Eine Chat-Model-Credential, also einen gespeicherten API-Zugang für das Sprachmodell, das die Antworten formuliert.
  • Eine Embeddings-Credential, z. B. für den Node Embeddings OpenAI oder einen anderen unterstützten Anbieter. Was Embeddings sind, erklärt dieses Kapitel Schritt für Schritt.
  • Für das Beispiel keine echten internen Dateien: Wir erzeugen fiktive Teamhandbuch-Texte direkt im Workflow.
Simple Vector Store nur als Lernspeicher Den Simple Vector Store findest du in älteren Anleitungen als In-Memory Vector Store; n8n hat ihn mit 1.82 im März 2025 umbenannt. Er hält alle Daten nur im Arbeitsspeicher der n8n-Instanz. Zum Lernen ist das ideal. Für echte Dokumente nicht, aus drei Gründen: Nach einem Neustart ist der Inhalt weg. Bei knappem Speicher räumt n8n ältere Stores selbst ab. Und die Memory Keys gelten instanzweit: Wer auf derselben Instanz einen Simple Vector Store einfügt, sieht deinen Key in der Auswahlliste und kann mitlesen. Für echte Dokumente nimm später Qdrant, PGVector, Pinecone, Supabase oder einen anderen persistenten Vector Store, also einen, der Daten dauerhaft speichert.
Grenzen des Lernspeichers Auf n8n Cloud gelten rund 100 MB (etwa 8000 Dokumente) und sieben Tage ohne Zugriff als Grenze. Selbst gehostet stellst du beides über N8N_VECTOR_STORE_MAX_MEMORY und N8N_VECTOR_STORE_TTL_HOURS ein. Fürs Durcharbeiten dieses Kapitels musst du dich darum nicht kümmern.

Das Ziel

Wir bauen zwei Workflows. Der erste lädt vier kleine Dokumente in einen Vector Store. Der zweite nimmt eine Chatfrage entgegen, sucht passende Textstellen und beantwortet die Frage nur aus diesen Textstellen.

RAG in einem Satz RAG heißt: erst passende Textstellen suchen, dann das Modell mit diesen Textstellen antworten lassen. Ohne Suche ist es nur ein normaler Chat. Ohne strenge Antwortregel halluziniert der Chat trotzdem.

Die Bausteine

Diese sechs Bausteine setzt du gleich zusammen. Zwei Begriffe vorab: Ein Chunk ist ein Textabschnitt, in den lange Dokumente zerlegt werden. Ein Vektor ist eine lange Zahlenreihe, die die Bedeutung eines Textes beschreibt. Mit diesen Zahlen kann n8n ausrechnen, welche Texte einander ähnlich sind.

BausteinAufgabeTypischer Fehler
Default Data Loadermacht aus Datei oder JSON ein Dokumentfalsches Feld wird geladen
Text Splitterzerlegt lange Texte in ChunksChunks sind zu groß oder ohne Überlappung
Embeddingswandelt Text in Zahlenvektoren umanderes Modell beim Laden als beim Suchen
Vector Storespeichert und findet ähnliche Chunksalte und neue Daten werden versehentlich gemischt
Retrieverholt die besten Treffer zur Fragezu wenige Treffer oder keine Metadaten
Q&A Chainformuliert aus Frage und Treffern eine AntwortAntwortet auch, wenn der Kontext nichts hergibt
Skeptische Einordnung RAG ist keine Wahrheitsmaschine. Es erhöht nur die Chance, dass die Antwort aus deinen Dokumenten stammt. Ob sie am Ende stimmt, hängt an vier Dingen: was in den Dokumenten steht, wo du die Chunks trennst, ob du die Quelle mit ausgibst und ob du mit Fragen testest, die nicht beantwortbar sein dürfen.

Schritt 1: Lade-Workflow erstellen

Der Lade-Workflow füllt den Vector Store. Er läuft nur, wenn du Dokumente neu einliest, nicht bei jeder Nutzerfrage.

  1. Neuen Workflow anlegen

    Erstelle einen Workflow und nenne ihn RAG Wissen laden.

  2. Manual Trigger hinzufügen

    Wähle als ersten Node Trigger manually. So startet der Workflow nur, wenn du selbst klickst. Ein Ladeprozess soll nicht aus Versehen automatisch laufen.

  3. Auto-Save prüfen

    n8n speichert deinen Entwurf (Draft) von selbst. Warte kurz, bis das passiert ist.

Warum kein Schedule? Ein automatischer Reload kann den Store leeren oder doppelte Chunks erzeugen. Baue erst einen manuell geprüften Ladeprozess. Automatisierung kommt danach.

  1. Code-Node anhängen

  2. Node benennen

    Nenne ihn Demo-Dokumente.

  3. Modus prüfen

    Prüfe, dass im Feld Mode die Option Run Once for All Items gewählt ist.

  4. Code einfügen

Schritt 3: Simple Vector Store zum Einfügen anlegen

Jetzt speicherst du die Dokumente als Vektoren. Der Vector Store ist ein sogenannter Root-Node: ein Hauptknoten, an den unten kleinere Hilfs-Nodes für Embeddings, Data Loader und Text Splitter andocken. Diese Anschlüsse füllst du in den Schritten 4 bis 6.

  1. Vector Store anhängen

    Ziehe von Demo-Dokumente eine Linie ins Leere. Tippe im Suchfenster simple vector store und wähle den Node aus.

  2. Operation Mode wählen

    Öffne den neuen Node. Das oberste Feld heißt Operation Mode. Ab Werk steht dort Retrieve Documents (As Vector Store for Chain/Tool). Stelle es auf Insert Documents um. Hast du den Node über die Aktion Add documents to vector store eingefügt, steht das Richtige schon drin.

  3. Memory Key setzen

    Der Memory Key ist das Namensschild deines Speichers. Das Feld hat zwei Modi. Schalte links auf Manual und tippe werkbuch-teamhandbuch-demo ein. Der andere Modus From List zeigt vorhandene Keys an; beim ersten Mal gibt es noch keinen. Merke dir den Key: Beim Abfragen brauchst du später exakt denselben.

  4. Clear Store einschalten

    Schalte Clear Store ein. Der Schalter ist ab Werk aus, und beim Lernbeispiel willst du ihn an haben: So ersetzt jeder Testlauf den alten Demo-Store, statt Chunks zu verdoppeln.

  5. Node benennen

    Nenne den Node Teamhandbuch speichern.

Memory Key ist die Datenbankadresse Der Memory Key verbindet Laden und Abfragen. Ein Tippfehler wirft dabei meist gar keinen Fehler. Er legt einfach einen zweiten, leeren Store an, und die Chain antwortet brav, sie wisse nichts.

Schritt 4: Embeddings verbinden

Embeddings übersetzen Text in Zahlenvektoren. Wichtig: Beim Speichern und beim späteren Suchen muss dasselbe Embedding-Verfahren laufen. Sonst vergleichst du Zahlen aus zwei verschiedenen Koordinatensystemen, und die Suche findet Unsinn.

  1. Embedding-Anschluss öffnen

    Schließe die Detailansicht, damit du den Canvas siehst. Unter dem Vector-Store-Node hängt ein Anschluss mit dem Namen Embedding, im Singular. Klicke auf das + darunter.

  2. Embedding-Node wählen

    Wähle z. B. Embeddings OpenAI oder einen anderen von dir eingerichteten Anbieter.

  3. Credential wählen

    Wähle im neuen Node deine Credential aus. Lege API-Keys nie als Klartext in Nodes ab.

  4. Modell stabil halten

    Im Feld Model steht beim Node Embeddings OpenAI ab Werk text-embedding-3-small. Für vier kurze Texte reicht das mit Abstand. Lass den Wert stehen und ändere ihn nicht zwischen Laden und Abfragen.

Modellwechsel heißt meist neu indexieren Wenn du später das Embedding-Modell wechselst, lade die Dokumente neu in den Store. Misch alte und neue Vektoren nicht: Sie liegen in verschiedenen Räumen, und die Ähnlichkeitswerte dazwischen bedeuten nichts.

Schritt 5: Data Loader konfigurieren

Der Data Loader entscheidet, welcher Teil deiner Items überhaupt als Dokumenttext in den Store geht. Was hier nicht im Text landet, kann später keine Antwort werden.

  1. Data-Loader-Anschluss öffnen

    Klicke am Vector-Store-Node auf den Anschluss Document und wähle Default Data Loader.

  2. Type of Data setzen

    Type of Data steht schon auf JSON. Die zweite Option wäre Binary, die brauchst du erst bei PDFs.

  3. Mode setzen

    Setze Mode von Load All Input Data auf Load Specific Data. Wir laden nicht blind das ganze JSON.

  4. Textvorlage eintragen

    Jetzt erscheint das Feld Data. Schalte es zuerst auf Expression um (die kleinen Reiter Fest/Expression erscheinen, sobald du mit der Maus über dem Feld bist), sonst landen die geschweiften Klammern wörtlich als Text im Store. Trage dann die folgende Vorlage ein. Die doppelten geschweiften Klammern sind Expressions: n8n setzt an diesen Stellen den Wert aus dem jeweiligen Item ein.

  Load Specific Data
Titel: {{ $json.title }}
Thema: {{ $json.topic }}
Quelle: {{ $json.source }}

{{ $json.text }}

  1. Metadaten ergänzen

    Scrolle im Default Data Loader nach unten zu Options, klicke Add Option und wähle Metadata. Über Add property legst du je einen Eintrag mit Name und Value an. Auch die Value-Felder sind Expressions: Stelle jedes einzelne auf Expression um, bevor du den Wert einträgst. Nutze mindestens die folgenden vier.

NameValueWarum

title{{ $json.title }}lesbare Quellenangabe

Schritt 6: Text Splitter anschließen

Unsere Demo-Texte sind kurz. Trotzdem bauen wir den Splitter jetzt schon ein, weil echte Dokumente selten kurz sind.

  1. Text Splitting auf Custom setzen

    Setze im Default Data Loader Text Splitting von Simple auf Custom. Simple würde stumm mit 1000 Zeichen und 200 Überlappung schneiden, ohne dass du einen Node dafür siehst.

  2. Splitter verbinden

    Jetzt taucht am Data Loader der Anschluss Text Splitter auf. Klicke darauf und wähle Recursive Character Text Splitter.

  3. Chunk Size setzen

    Setze Chunk Size für das Demo von 1000 auf 600.

  4. Chunk Overlap setzen

    Setze Chunk Overlap auf 80. Achtung, hier steht ab Werk 0. Mit Überlappung gehen Begriffe an Chunk-Grenzen nicht sofort verloren.

Warum Recursive Character? Der rekursive Splitter versucht Absätze, Sätze und Wörter möglichst zusammenzuhalten. Für normale Texte ist das ein besserer Startpunkt als stumpfes Schneiden nach fester Zeichenlänge.

Schritt 7: Dokumente in den Store laden

Jetzt führst du den kompletten Lade-Workflow aus.

  1. Canvas schließen

    Schließe alle Detailansichten, damit du den Lade-Workflow vollständig siehst.

  2. Auto-Save prüfen

    Warte kurz, bis n8n den Draft automatisch gespeichert hat.

  3. Workflow starten

    Klicke unten am Canvas auf Execute workflow. Bis n8n 1.x hieß derselbe Knopf Test workflow. Die Nodes werden nacheinander grün. Grün heißt: Dieser Node ist ohne Fehler durchgelaufen.

  4. Output prüfen

    Öffne Teamhandbuch speichern mit einem Doppelklick. Rechts steht pro gespeichertem Chunk ein Item mit den Feldern pageContent und metadata. Bei vier kurzen Demo-Texten und Chunk Size 600 sind das genau vier Items. Damit ist dein Wissensspeicher gefüllt.

  5. Keine echten Geheimnisse laden

    Prüfe noch einmal: Im Demo-Store stehen nur fiktive Daten. Keine echten Kundendaten, Tokens oder Personalakten.

Wenn der Store leer bleibt Prüfe drei Dinge in dieser Reihenfolge: Memory Key gesetzt? Embeddings verbunden? Data Loader lädt wirklich {{ $json.text }}? Ohne diese drei Punkte hat die spätere Q&A Chain nichts zu suchen.

Schritt 8: Frage-Workflow erstellen

Der zweite Workflow fragt den Store ab. Er läuft bei jeder Chatnachricht.

  1. Neuen Workflow anlegen

    Erstelle einen Workflow und nenne ihn RAG Teamhandbuch fragen.

  2. Chat Trigger hinzufügen

    Füge als ersten Node einen Chat Trigger hinzu. Er startet den Workflow bei jeder eingetippten Chatnachricht.

  3. Chat privat lassen

    Lasse den Schalter Make Chat Publicly Available zunächst aus. Du testest erst einmal im internen Chat von n8n.

  4. Startnachricht später setzen

    Das Feld Initial Message(s) siehst du im privaten Modus noch nicht. Das ist normal. Es erscheint erst, wenn Make Chat Publicly Available an ist und Mode auf Hosted Chat steht. Merk dir den Satz Frag mich etwas zum fiktiven Teamhandbuch. für später und tippe deine Testfragen bis dahin selbst ein.

Schritt 9: Question and Answer Chain einbauen

Eine Chain ist eine feste Kette von Arbeitsschritten. Für ein reines Dokumenten-Q&A ist sie oft besser als ein Agent, denn sie entscheidet nicht frei über Tools. Sie bekommt eine Frage, nutzt den Retriever und formuliert eine Antwort. Mehr nicht.

  1. Q&A Chain anhängen

    Ziehe vom Chat Trigger eine Linie ins Leere, suche question answer und wähle Question and Answer Chain.

  2. Node benennen

    Nenne den Node Teamhandbuch beantworten.

  3. Prompt-Quelle prüfen

    Source for Prompt (User Message) steht schon auf Connected Chat Trigger Node. Lass es so. Die Chain holt sich dann das Feld chatInput vom Chat Trigger. Das Feld Prompt (User Message) darunter zeigt ausgegraut {{ $json.chatInput }}. Ein einzelnes Feld namens Query gab es nur bis zur Node-Version 1.2; wundere dich nicht, wenn ältere Anleitungen es erwähnen.

  4. Antwortregel eintragen

    Klicke unten auf Options, dann auf Add Option, und wähle System Prompt Template. Im Feld steht bereits eine englische Standardregel. Ersetze sie durch den folgenden Text. Wichtig: Der Platzhalter {context} muss drinbleiben. An dieser Stelle setzt n8n die gefundenen Chunks ein.

  System Prompt Template · Q&A Chain
Du beantwortest Fragen zu einem Teamhandbuch.
Nutze ausschließlich die folgenden gefundenen Textstellen.
Wenn die Antwort dort nicht steht, sage genau:
"Das steht nicht in den geladenen Dokumenten."
----------------
Context: {context}
Antwortregel ins System Prompt Template Eine RAG-Antwort braucht eine klare Bremse. Sonst nutzt das Modell sein Allgemeinwissen, sobald der Retriever nichts Passendes findet. Die mitgelieferte Standardregel sagt zwar auch schon „just say that you don't know“, aber sie ist englisch und weich formuliert. Ein eigener, deutscher Satz ist im Test besser prüfbar.

Schritt 10: Model verbinden

Die Q&A Chain braucht ein Sprachmodell, um aus den gefundenen Chunks eine Antwort zu formulieren.

  1. Model-Anschluss öffnen

    Unter der Q&A Chain hängt ein Anschluss mit dem Namen Model. Beim AI Agent heißt derselbe Anschluss Chat Model; bei den Chains steht dort nur Model. Klicke auf das + darunter.

  2. Modell wählen

    Wähle dasselbe Chat Model, das du schon in Kapitel 20 genutzt hast, etwa OpenAI Chat Model, und dann deine Credential.

  3. Temperatur niedrig setzen

    Klicke im Model-Node auf Add Option, wähle Sampling Temperature und setze den Wert auf 0.2. Voreingestellt sind 0.7. Ein niedriger Wert macht die Antworten weniger kreativ, und genau das willst du bei Dokumenten-Q&A.

Schritt 11: Retriever und Vector Store verbinden

Jetzt bekommt die Chain Zugriff auf die gespeicherten Dokumente. Der Retriever ist der Baustein, der zur Frage die passendsten Chunks aus dem Store holt.

  1. Retriever-Anschluss öffnen

    Klicke an der Q&A Chain auf den Anschluss Retriever und wähle Vector Store Retriever.

  2. Limit prüfen

    Der Vector Store Retriever hat genau ein Feld: Limit, ab Werk 4. Für vier Demo-Dokumente passt das. Lass es stehen.

  3. Vector Store anschließen

    Klicke am Retriever auf Vector Store und wähle Simple Vector Store.

  4. Operation Mode wählen

    Setze Operation Mode auf Retrieve Documents (As Vector Store for Chain/Tool). Das ist hier bereits die Voreinstellung. In diesem Modus hat der Vector Store selbst kein Limit-Feld, die Trefferzahl kommt vom Retriever.

  5. Memory Key wiederholen

    Setze Memory Key exakt auf werkbuch-teamhandbuch-demo, denselben Key wie im Lade-Workflow. Weil der Lade-Workflow schon gelaufen ist, findest du den Key jetzt auch bequem über From List. Das ist der sichere Weg ohne Tippfehler.

  6. Embeddings verbinden

    Verbinde auch beim abfragenden Vector Store denselben Embedding-Node wie im Lade-Workflow, also Embeddings OpenAI mit text-embedding-3-small.

  7. Rerank Results aus lassen

    Der Schalter Rerank Results bleibt aus. Er verlangt einen zusätzlichen Reranker-Sub-Node, und bei vier Dokumenten gibt es nichts umzusortieren.

Schritt 12: Erste Fragen testen

Beim Testen prüft fast jeder nur den Erfolgsfall. Ein RAG-System muss aber auch sauber sagen können, dass etwas nicht in den Dokumenten steht.

  1. Chat öffnen

    Klicke unten am Canvas auf Open chat. Ein Chatfenster öffnet sich, derselbe interne Testchat wie in Kapitel 20. Veröffentlichen musst du dafür nichts.

  2. P1-Frage stellen

    Schreibe: Wie schnell muss P1 eskaliert werden?

  3. Antwort prüfen

    Die Antwort muss 15 Minuten und den Kontext P1 nennen.

  4. Spesenfrage stellen

    Schreibe: Welche Spesen brauchen vorher eine Freigabe?

  5. Antwort prüfen

    Die Antwort muss über 250 Euro nennen. Wenn sie allgemeine Reiserichtlinien erfindet, ist die Antwortregel zu schwach.

  6. Gegenfrage stellen

    Schreibe: Wie lautet die Homeoffice-Regel für Freitage?

  7. Nichtwissen prüfen

    Die erwartete Antwort ist: Das steht nicht in den geladenen Dokumenten.

Wenn die Gegenfrage trotzdem beantwortet wird Dann nutzt das Modell Allgemeinwissen. Verschärfe das System Prompt Template, senke die Sampling Temperature und prüfe, ob der Retriever irrelevante Chunks liefert.

Schritt 13: Execution statt nur Chat lesen

Eine gute Antwort im Chat beweist nicht, dass RAG korrekt gearbeitet hat. Öffne deshalb die Execution, also das Protokoll eines einzelnen Laufs, und prüfe die Zwischenschritte.

  1. Execution öffnen

    Stelle eine Testfrage im Chat. Öffne danach die zugehörige Ausführung des Frage-Workflows.

  2. Q&A Chain prüfen

    Prüfe die Eingabe: Kommt wirklich ein gefülltes chatInput an? Ist es leer oder null, meldet die Chain „No prompt specified“.

  3. Retriever prüfen

    Öffne den Vector Store Retriever oder den angeschlossenen Vector Store. Prüfe, welche Dokumente zurückkamen.

  4. Metadaten prüfen

    Suche nach doc_id, title, topic oder source. Ohne Metadaten kannst du Fehler später kaum debuggen.

Trefferqualität vor Antwortqualität Wenn der Retriever falsche Chunks liefert, kann das Modell die Antwort kaum retten. Debugge erst die Suche, dann den Prompt.

Schritt 14: Quellen sichtbarer machen

Die einfache Q&A Chain ist bequem, aber nicht immer transparent genug. Wenn du Quellen zwingend anzeigen willst, baue eine explizitere Variante: erst suchen, dann Kontext und Quellen an das Modell geben.

VarianteWorkflowVorteil
EinfachChat Trigger → Q&A Chain → Antwortschnell aufgebaut, wenig Nodes
TransparenterChat Trigger → Vector Store Get Many → Code-Kontext → Basic LLM ChainQuellen und Treffer lassen sich sichtbar formatieren
AgentischChat Trigger → AI Agent → Vector Store Question Answer Toolsinnvoll, wenn der Chat mehrere Werkzeuge braucht
Empfehlung Für reine Wissensfragen: Q&A Chain. Für prüfbare Quellenanzeigen: direkte Suche plus eigener Prompt. Für mehrere Werkzeuge: Agent mit Vector-Store-Tool.

Schritt 15: Agent-Variante einordnen

Wenn du an den Agenten aus Kapitel 20 anknüpfst, nutzt du nicht die Q&A Chain als Hauptknoten, sondern ein Tool am Agenten.

  1. AI Agent verwenden

    Nutze einen AI Agent nur dann, wenn der Chat außer RAG noch weitere Entscheidungen treffen muss. Stand Juli 2026 (n8n 2.32.x) braucht der Agent ein Chat Model und mindestens ein Tool; für reines Q&A bleibt die Chain einfacher.

  2. Vector Store Question Answer Tool anschließen

    Verbinde am Tool-Anschluss des Agenten das Vector Store Question Answer Tool.

  3. Beschreibung präzise setzen

    Setze Description of Data z. B. auf fiktive Teamhandbuch-Regeln zu Urlaub, Spesen, Onboarding und Support.

  4. Limit setzen

    Limit steht ab Werk auf 4. Für unsere vier Dokumente passt das.

  5. Vector Store verbinden

    Verbinde das Tool mit demselben Simple Vector Store und demselben Memory Key.

  6. Eigenes Model verbinden

    Das Tool hat einen zweiten Pflichtanschluss: Model. Es fasst die gefundenen Chunks nämlich selbst zusammen, bevor es dem Agenten antwortet. Hänge dort ein Chat Model an, sonst bricht der Lauf ab.

Tool-Namen nüchtern halten Seit Node-Version 1.1 nimmt das Tool seinen Namen vom Node auf dem Canvas; ein eigenes Feld Data Name gab es nur in Version 1. Nutze für den Node-Namen einfache Buchstaben, Zahlen, Leerzeichen, Bindestriche oder Unterstriche. Sonderzeichen können Modell- oder Tool-Aufruffehler verursachen.

Schritt 16: Chunking verbessern

Chunking entscheidet, ob relevante Zusammenhänge gemeinsam gefunden werden. Zu kleine Chunks verlieren Kontext. Zu große Chunks verwässern die Suche.

DokumenttypStartwertWorauf achten?
FAQ / kurze Regeln400–800 Zeichen, 50–100 OverlapFrage und Antwort zusammenhalten
Handbuchseiten800–1400 Zeichen, 100–200 OverlapAbschnitte nicht mitten in Listen trennen
Technische Doku700–1200 Zeichen, 100–200 OverlapCodeblöcke und Überschriften zusammenhalten
Verträge / Richtlinienkleiner starten, Metadaten stark nutzenParagraf, Version und Gültigkeit als Metadata speichern
Warum die Chunk-Größe so viel entscheidet Mischt ein Chunk mehrere Themen, wird sein Vektor unscharf: Die Suche findet ihn für alles ein bisschen und für nichts richtig. Zerfällt ein Thema über zu viele kleine Chunks, fehlt beim Antworten der Zusammenhang. Chunk Size und Overlap sind also keine Nebensache. Wer sie nach Gefühl setzt, verstellt die Suche, ohne es zu merken.

Schritt 17: Produktionsspeicher auswählen

Für echte Daten brauchst du einen persistenten Vector Store. n8n bringt dafür fertige Nodes mit, unter anderem für Qdrant, PGVector, Pinecone, Supabase, Chroma, Redis, Milvus, Weaviate, MongoDB Atlas und Azure AI Search. Die Auswahl fühlt sich technisch an, entschieden wird sie aber an drei betrieblichen Fragen: Wer darf lesen? Wie wird gelöscht? Wie wird neu indexiert?

StoreGeeignet fürSkeptische Frage
Simple Vector StoreLernen, Prototypen, DemosWas passiert nach Neustart oder bei mehreren Nutzern?
PGVectorTeams mit bestehender Postgres-InfrastrukturWer betreibt Backups, Migrationen und Zugriffskontrolle?
Qdrantdedizierte Vektorsuche, lokal oder CloudWie werden Collections versioniert und gelöscht?
Pinecone / Supabaseverwaltete DiensteWelche Daten verlassen dein System und welche Kosten entstehen?
Löschen mitdenken RAG-Systeme vergessen nicht automatisch. Wenn ein Dokument veraltet oder rechtlich zu löschen ist, brauchst du eine Strategie für Löschung, Neuindexierung und Versionierung. Der Simple Vector Store kennt dafür nur Clear Store, also alles oder nichts. Manche persistenten Stores, etwa Pinecone, haben zusätzlich den Operation Mode Update Documents mit einem Feld ID. Prüf das, bevor du dich für einen Store entscheidest.

Schritt 18: Konkrete Testfälle anlegen

RAG ohne Testfragen ist Bauchgefühl. Lege eine kleine Testmatrix an und prüfe sie nach jedem Daten- oder Promptwechsel.

Teste auch Nichtwissen Ein RAG-System, das alles beantwortet, ist nicht hilfreich. Es ist gefährlich plausibel. Die beste Schutzfrage ist oft eine Frage, deren Antwort absichtlich nicht im Store steht.

Selbsttest

  • Warum ist Memory kein Ersatz für RAG?
  • Warum braucht der Frage-Workflow denselben Memory Key wie der Lade-Workflow?
  • Welche drei Dinge prüfst du zuerst, wenn der Retriever nichts findet?
  • Warum ist der Simple Vector Store für echte interne Dokumente problematisch?
  • Warum muss ein RAG-Test auch Fragen enthalten, deren Antwort nicht im Store steht?
Antworten 1) Memory speichert Gesprächsverlauf, RAG sucht in einem Dokumentenbestand. · 2) Weil der Key den gespeicherten Vektorraum adressiert. · 3) Store geladen, Memory Key gleich, Embeddings verbunden. · 4) Weil Daten nicht dauerhaft garantiert sind und Keys instanzweit zugänglich sein können. · 5) Weil Nichtwissen der wichtigste Test gegen Halluzination ist.

Eine Übung zum Schluss. Ändere im Data Loader die Vorlage im Feld Data so, dass Titel, Thema und Quelle nicht mehr im Dokumenttext stehen, sondern nur noch als Metadaten. Lade den Store neu. Stelle dann dieselben fünf Testfragen aus Schritt 18 und notiere, welche Antworten kippen. Du hast an keinem Prompt gedreht, nur drei Zeilen im Loader gelöscht. Genau darum geht in der Praxis so viel Zeit in die Loader-Vorlage. Das nächste Kapitel lässt die KI wieder liegen und kümmert sich um Betriebsstruktur: wiederverwendbare Sub-Workflows und saubere Grenzen zwischen ihnen.
