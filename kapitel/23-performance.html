Performance, Batching & Rate-Limits

Deine Workflows laufen inzwischen korrekt. Jetzt sollen sie auch berechenbar laufen. Zwei neue Begriffe dafür: Batching heißt, Daten in kleinen Gruppen zu verarbeiten statt alle auf einmal. Ein Rate-Limit ist eine Grenze, die ein Dienst setzt, zum Beispiel „höchstens 5 Anfragen pro Sekunde“. Gut zu wissen: n8n verarbeitet mehrere Items meistens automatisch. Batching brauchst du nur, wenn ein Dienst langsam ist, Limits setzt oder große Datenmengen sonst unkontrolliert durch den Workflow laufen.

ca. 18 Minuten Niveau: Fortgeschrittene Grundlagen Voraussetzung: Kapitel 5, 8, 10, 22

Was du brauchst

  • Eine n8n-Instanz, lokal oder in der Cloud.
  • Keine API-Credentials: Wir bauen uns die externe API mit Code-Nodes selbst nach.
  • Grundverständnis für Items, IF und Schleifen (Kapitel 5, 8 und 10).
  • Bewusst kleine Testdaten. Mit echten Massendaten wird das Thema schnell unübersichtlich.
Mehr auf einmal ist nicht automatisch schneller Ein Workflow kann an API-Limits, Datenbankverbindungen, Speicher, Dateigrößen oder Modellkosten scheitern. Das Ziel ist kontrollierter Durchsatz: eine Menge pro Zeit, die der Dienst verkraftet. Alles gleichzeitig loszuschicken bringt dich da selten hin.
Stand Juli 2026: Code-Nodes und Task Runner Die Beispiele nutzen Code-Nodes, nicht die alten Function-Nodes. Seit n8n 2.0 laufen Code-Nodes standardmäßig in Task Runnern, also in einer abgeschotteten Umgebung. Du musst dafür nichts einschalten; die frühere Variable N8N_RUNNERS_ENABLED ist seit 2.0 überflüssig. Eine Folge merkst du beim Schreiben von Code: Der Zugriff auf Umgebungsvariablen über process.env ist im Code-Node standardmäßig gesperrt. Wer ihn wirklich braucht, setzt beim Self-Hosting N8N_BLOCK_ENV_ACCESS_IN_NODE=false. Warum n8n davon abrät, steht in Kapitel 9. Für dieses Kapitel brauchst du das alles nicht, unsere Beispiele laufen ohne jede Einstellung.

Das Ziel

Du baust einen Workflow, der 23 erfundene API-Aufträge in kleinen Gruppen verarbeitet. Die Gruppen bildet der Node Loop Over Items. In der Node-Suche und in älteren Anleitungen heißt er auch Split in Batches, es ist derselbe Node. Dazu kommen ein Code-Node, der eine API-Antwort nachbaut, ein Wait-Node als Bremse (er lässt den Workflow kurz warten) und am Ende eine Zusammenfassung. So lernst du das Muster ohne echte Fremddienste und ohne Kosten.

Performance in einem Satz Miss erst, bremse dann gezielt. Ohne Messpunkt weißt du nicht, ob dein Problem CPU, Speicher, API-Limit, Dateigröße, Netzwerk oder schlechte Workflow-Struktur ist.

Die drei Hebel

Drei Stellschrauben entscheiden, wie kontrolliert dein Workflow läuft. Alle drei baust du gleich selbst ein.

HebelWirkungRisiko
Batchgrößebestimmt, wie viele Items pro Runde verarbeitet werdenzu groß: Limits, Speicher, Timeouts
Wartezeitsenkt Anfragefrequenz und glättet Lastzu lang: Workflow dauert unnötig
Fehlerstrategieentscheidet, ob ein Fehler alles stoppt oder markiert wirdzu weich: echte Fehler werden übersehen
Skeptische Einordnung Viele n8n-Nodes verarbeiten mehrere Items automatisch, ganz ohne Schleife. Ein Loop ist daher nicht der Normalfall. Du nutzt ihn nur, wenn eine äußere Grenze das verlangt: ein Rate-Limit, Pagination (Daten kommen seitenweise), eine feste Batchgröße, eine Pause oder eine kontrollierte Reihenfolge.

Schritt 1: Workflow anlegen

Wir starten mit erfundenen Testdaten statt mit einem echten Dienst. Der Vorteil: Du bestimmst selbst, wie viele Daten kommen und wann ein Fehler auftaucht.

  1. Neuen Workflow erstellen

    Lege wie in Kapitel 5 einen neuen, leeren Workflow an. Nenne ihn Batching und Rate-Limits lernen.

  2. Manual Trigger hinzufügen

    Füge als ersten Node einen Manual Trigger hinzu. Im Node-Panel heißt der Eintrag Trigger manually, auf dem Canvas beschriftet n8n ihn mit When clicking ‘Execute workflow’. Beides ist derselbe Node.

  3. Code-Node anhängen

    Ziehe vom Trigger eine Verbindung ins Leere und wähle in der Suche Code. Nenne den neuen Node Demo-Aufträge.

  4. Modus setzen und Code einfügen

    Öffne den Node und stelle oben Mode auf Run Once for All Items. Das heißt: Der Code läuft einmal für alle Items gemeinsam. Ersetze dann den vorhandenen Beispielcode durch den Block unten. Er erzeugt 23 Übungsdatensätze.

  Code · Demo-Aufträge
const jobs = Array.from({ length: 23 }, (_, index) => {
  const id = index + 1;
  return {
    json: {
      job_id: `job-${String(id).padStart(3, '0')}`,
      customer: `Demo-Kunde ${id}`,
      amount_eur: 20 + id * 3,
      priority: id % 7 === 0 ? 'hoch' : 'normal'
    }
  };
});

return jobs;

  1. Node ausführen

    Klicke auf Schritt ausführen. Rechts im Ausgabe-Bereich erscheinen 23 Items, von job-001 bis job-023. Siehst du sie? Dann steht dein Datenstrom. Wenn nicht: Prüfe, ob der Modus auf Run Once for All Items steht und der Code vollständig kopiert wurde.

Schritt 2: Loop Over Items hinzufügen

Der Loop-Node teilt die 23 Items in kleinere Gruppen, die Batches. Bei Batchgröße 5 entstehen vier volle Batches mit je fünf Items und ein Rest-Batch mit drei Items.

  1. Loop-Node anhängen

    Ziehe von Demo-Aufträge eine Verbindung ins Leere und suche Loop Over Items. Klicke den Treffer an.

  2. Batchgröße setzen

    Öffne den Node. Setze Batch Size auf 5. Voreingestellt steht dort 1.

  3. Node benennen

    Nenne ihn 5er Batches.

  4. Ausgänge beachten

    Schau auf die rechte Seite des Nodes: Er hat zwei Ausgänge. Oben sitzt done (englisch für „fertig“). Aus ihm kommt erst etwas heraus, wenn alle Batches durch sind. Darunter sitzt loop mit dem jeweils aktuellen Batch. Diese Reihenfolge verwechselt man leicht, weil ältere Screenshots und Videos die umgekehrte Belegung zeigen. Kapitel 10 erklärt sie ausführlicher.

Kein zusätzlicher IF-Node für „alle Items fertig“ Für den Standardfall beendet Loop Over Items die Verarbeitung selbst und schaltet danach auf den done-Ausgang. Einen Abbruch-IF brauchst du nur bei selbstgebauten Schleifen, etwa bei unbekannter Pagination.

Schritt 3: API-Aufruf simulieren

Statt eine echte API aufzurufen, tut ein Code-Node so, als wäre er eine. Er nimmt den aktuellen Batch entgegen und hängt an jedes Item eine „Antwort“ an.

  1. Code-Node am Loop-Ausgang anhängen

    Ziehe vom unteren loop-Ausgang von 5er Batches eine Verbindung ins Leere und wähle einen neuen Code-Node. Der häufigste Fehler in diesem Kapitel: hier aus Versehen den oberen done-Ausgang erwischen.

  2. Node benennen

    Nenne ihn API simulieren.

  3. Modus setzen

    Stelle Mode auf Run Once for All Items, damit der Batch gemeinsam verarbeitet wird.

  4. Code einfügen

    Ersetze den Beispielcode durch diesen Block:

  Code · API simulieren
const batch = $input.all();
const batchSize = batch.length;
const now = new Date().toISOString();

return batch.map((item, index) => {
  const job = item.json;
  const simulatedStatus = batchSize > 5 ? 429 : 200;

  return {
    json: {
      ...job,
      batch_size: batchSize,
      batch_position: index + 1,
      api_status: simulatedStatus,
      api_message: simulatedStatus === 200
        ? 'verarbeitet'
        : 'zu viele Anfragen in diesem Batch',
      processed_at: now
    }
  };
});

Kurz übersetzt: $input.all() holt alle Items des aktuellen Batches. Der Code hängt an jedes Item ein Feld api_status an. 200 heißt „alles ok“. Hat der Batch mehr als fünf Items, gibt es stattdessen 429, den typischen Statuscode für „zu viele Anfragen“. Genau so reagieren echte APIs, wenn du ihr Limit überschreitest.

Warum hier Batchgröße 5? Im Beispiel ist 5 der erlaubte Grenzwert. In der echten Welt liest du diesen Wert in der API-Dokumentation: Anfragen pro Sekunde, pro Minute, pro Tag oder maximale Datengröße pro Anfrage.

Schritt 4: Wartezeit einbauen

Eine Pause nach jedem Batch senkt die Anfragefrequenz. Das ist das einfachste Muster gegen Rate-Limits: Batch verarbeiten, warten, nächsten Batch holen.

  1. Wait-Node anhängen

    Ziehe von API simulieren eine Verbindung ins Leere und wähle den Wait-Node.

  2. Node benennen

    Nenne ihn 1 Sekunde warten.

  3. Wartezeit setzen

    Öffne den Node. Lass Resume auf After Time Interval stehen, das bedeutet „nach einer festen Zeitspanne weitermachen“. Darunter stehen Wait Amount mit 5 und Wait Unit mit Seconds. Setze Wait Amount auf 1. Die Einheit bleibt auf Sekunden.

  4. Zurück zum Loop verbinden

    Ziehe den Ausgang des Wait-Nodes zurück auf den Eingang von 5er Batches. Diese Verbindung nach hinten schließt die Schleife: Nach der Pause holt der Loop den nächsten Batch.

  5. Workflow ausführen

    Führe den Workflow aus. Bei 23 Items und Batchgröße 5 laufen fünf Schleifenrunden. Du erkennst sie daran, dass API simulieren und der Wait-Node mehrfach nacheinander aufleuchten. Der ganze Lauf dauert gut fünf Sekunden. Das ist gewollt, nicht kaputt.

Überschlagsrechnung Durchsatz ≈ Batchgröße / Wartezeit. Bei 5 Items und 1 Sekunde Pause sind das grob 5 Items pro Sekunde, ohne Node-Laufzeit mitzuzählen.
Die Grenze liegt bei 65 Sekunden Wartet ein Workflow weniger als 65 Sekunden, schreibt n8n dafür nichts in die Datenbank. Die Ausführung bleibt im Arbeitsspeicher und macht nach der Pause dort weiter, wo sie war. Ab 65 Sekunden legt n8n die Ausführung in der Datenbank ab und holt sie danach wieder heraus. Kurze Pausen kosten dich also Arbeitsspeicher, lange Pausen kosten Datenbankarbeit. Unsere eine Sekunde liegt klar unter der Grenze, du musst dir hier keine Gedanken machen.

Schritt 5: Zusammenfassung am Done-Ausgang

Am done-Ausgang des Loop-Nodes kommen alle fertigen Items zusammen. Dort ergänzt du eine kleine Auswertung: Wie viele Items sind durchgelaufen? Welche Statuscodes waren dabei? Welche Batchgrößen hat der Loop gebildet?

  1. Code-Node am Done-Ausgang anhängen

    Ziehe vom oberen done-Ausgang von 5er Batches eine Verbindung ins Leere und wähle einen neuen Code-Node.

  2. Node benennen

    Nenne ihn Zusammenfassung.

  3. Modus setzen

    Stelle Mode auf Run Once for All Items.

  4. Code einfügen und testen

    Ersetze den Beispielcode durch den Block unten. Führe den Workflow danach einmal komplett aus. Am Ende zeigt Zusammenfassung genau ein Item mit total_items: 23 und rate_limited: 0. Dann hat alles geklappt.

  Code · Zusammenfassung
const items = $input.all();

const ok = items.filter((item) => item.json.api_status === 200).length;
const limited = items.filter((item) => item.json.api_status === 429).length;
const batchSizes = [...new Set(items.map((item) => item.json.batch_size))];

return [{
  json: {
    total_items: items.length,
    ok,
    rate_limited: limited,
    batch_sizes_seen: batchSizes,
    recommendation: limited === 0
      ? 'Batchgröße und Wartezeit sind für diesen Test stabil.'
      : 'Batchgröße senken oder Wartezeit erhöhen.'
  }
}];

Schritt 6: Grenzwert absichtlich brechen

Ein Test, bei dem nie etwas schiefgeht, ist zu schwach. Deshalb überschreitest du jetzt absichtlich die simulierte Grenze und schaust, ob dein Workflow das bemerkt.

  1. Batchgröße ändern

    Öffne 5er Batches und setze Batch Size testweise auf 8.

  2. Workflow erneut ausführen

    Starte den Workflow erneut. Die Batches sind jetzt größer als fünf, deshalb erzeugt API simulieren den Status 429.

  3. Zusammenfassung prüfen

    Öffne Zusammenfassung. rate_limited muss jetzt größer als 0 sein, und die Empfehlung rät zum Senken. Genau das wolltest du sehen: Dein Workflow erkennt das Limit.

  4. Batchgröße zurücksetzen

    Setze Batch Size wieder auf 5, damit der Workflow im Normalzustand bleibt.

429 ist kein „nochmal sofort“ Ein Rate-Limit-Fehler bedeutet fast immer: warten, weniger senden oder API-Regel lesen. Sofortiges Wiederholen kann das Limit verschärfen.

HTTP Request: eingebautes Batching

Wenn du später den echten HTTP Request-Node nutzt, musst du nicht jedes Mal Loop und Wait bauen. Der Node bringt Batching schon mit: Klicke unten im Node auf Add option und wähle Batching. Darunter erscheinen zwei Felder: Items per Batch für die Größe und Batch Interval für die Pause zwischen zwei Batches, angegeben in Millisekunden (1000 Millisekunden sind eine Sekunde). Für einfache API-Listen ist das kürzer als eine eigene Schleife. Die Tabelle zeigt, wann welche Variante passt.

VarianteNutze sie, wenn...Skeptische Frage
HTTP Request mit Batchingein einzelner API-Node gebremst werden sollReicht eine Pause zwischen Requests?
Loop Over Items + Waitmehrere Nodes pro Batch laufen oder die Logik sichtbar sein sollWo ist der Rücksprung, wo hängt done?
Retry On Failkurze, sporadische Fehler abgefangen werden sollenIst Wiederholen erlaubt oder erzeugt es Duplikate?
Concurrency-Limitdie ganze Instanz zu viele Produktiv-Ausführungen gleichzeitig startetBremst hier ein Workflow oder die Instanz?
Queue Modeviele Workflows/Executions parallel betrieben werdenIst die Infrastruktur dafür ausgelegt?
Pragmatische Reihenfolge Erst die Node-Einstellungen prüfen. Dann Batchgröße und Wait ergänzen. Bringt das nichts, begrenzt beim Self-Hosting N8N_CONCURRENCY_PRODUCTION_LIMIT die Zahl gleichzeitiger Produktiv-Ausführungen der ganzen Instanz, also der Läufe aus Webhooks und Trigger-Nodes. Ohne diese Variable gibt es keine Grenze. Über Queue Mode, Worker und Infrastruktur redest du zuletzt. Sonst löst du ein Workflow-Designproblem mit Betriebstechnik.

Execution-Daten klein halten

Zur Performance gehört auch, was liegen bleibt. Eine Execution ist ein gespeicherter Workflow-Lauf, und jede davon kann Daten speichern. Große JSON-Objekte, PDFs, Bilder oder vollständige API-Antworten machen die Fehlersuche bequem, aber Datenbank und Browser schwerfällig.

ProblemGegenmaßnahmeBegründung
riesige API-Antwortfrüh mit Edit Fields oder Code reduzierennur benötigte Felder weitertragen
Binärdaten im WorkflowDateien nicht unnötig durch alle Nodes schleppenkleinere Execution-Daten; seit n8n 2.0 landen Binärdaten im Dateisystem oder in der Datenbank statt im Arbeitsspeicher
Debug-Daten bleiben produktiv aktivTestfelder nach dem Aufbau entfernenweniger Rauschen, kleinere Historie
zu viele gespeicherte ExecutionsEXECUTIONS_DATA_MAX_AGE und EXECUTIONS_DATA_PRUNE_MAX_COUNT setzenvoreingestellt sind 336 Stunden und 10 000 Ausführungen
Frühes Reduzieren schlägt spätes Aufräumen Wenn ein Workflow 10 MB pro Item durch zehn Nodes trägt, hast du kein Anzeigeproblem. Du hast ein Datenmodellproblem.
Was n8n 2.x beim Betrieb mitbringt Bei der Datenbank hat n8n dir seit 2.0 Arbeit abgenommen. SQLite läuft jetzt immer über den Pooling-Treiber: WAL-Modus, eine schreibende Verbindung, ein Pool lesender Verbindungen. In den Benchmarks von n8n ist das bis zu zehnmal schneller als der alte Treiber. Wer Postgres nutzt, merkt davon nichts. Messen kannst du mit OpenTelemetry: n8n schreibt dann pro Ausführung einen Span workflow.execute und darin je Node einen Span node.execute. Von allein passiert das nicht. Du brauchst N8N_OTEL_ENABLED=true und einen Collector unter N8N_OTEL_EXPORTER_OTLP_ENDPOINT, im Queue Mode auf allen Instanzen. Wie lange n8n die Insights-Daten behält, steuert N8N_INSIGHTS_MAX_AGE_DAYS: 365 Tage sind voreingestellt, 730 Tage sind die Obergrenze. Für dein Lernsetup brauchst du nichts davon. Bevor du die erste eigene Messung aufsetzt, lohnt sich der Blick trotzdem.

Wenn etwas schiefgeht

Keine Sorge: Die meisten Loop-Probleme sind nur eine falsch gesteckte Verbindung. Prüfe zuerst, ob der Verarbeitungszweig am unteren loop-Ausgang hängt und der Wait-Node zurück zum Loop führt.

Selbsttest

  • Warum brauchst du in n8n nicht für jede Item-Liste einen Loop?
  • Welcher der beiden Ausgänge sitzt oben, loop oder done, und was liefert er?
  • Welche zwei Einstellungen reduzierst oder erhöhst du bei Status 429?
  • Warum kann Retry On Fail bei schreibenden Aktionen gefährlich sein?
  • Welche Daten solltest du möglichst früh aus einer großen API-Antwort entfernen?
Antworten 1) Viele Nodes verarbeiten Items automatisch. · 2) Oben sitzt done und läuft erst nach allen Batches; loop darunter liefert den aktuellen Batch. · 3) Batchgröße senken oder Wartezeit erhöhen. · 4) Weil Wiederholungen doppelte Datensätze, Zahlungen oder Nachrichten erzeugen können. · 5) Alles, was spätere Nodes nicht brauchen: Rohtexte, große Arrays, Debugfelder, Binärdaten.

Das Muster aus Batch, Pause und done-Zweig trägt dich durch die meisten Rate-Limits. Eine Sache löst es nicht: Ein Workflow, der auf deinem Rechner sauber durchläuft, kann auf dem Server an ganz anderen Stellen klemmen. Deshalb geht es als Nächstes um den Betrieb. Deployment, Umgebungsvariablen und Git sorgen dafür, dass der Weg zwischen Test und Produktion nachvollziehbar bleibt.
