Performance, Batching & Rate-Limits

In diesem Kapitel lernst du, Workflows nicht nur korrekt, sondern berechenbar laufen zu lassen. Der Kern ist einfach: n8n verarbeitet Items meistens automatisch. Batching brauchst du dann, wenn ein Dienst langsam ist, Limits setzt oder große Datenmengen sonst unkontrolliert durch den Workflow laufen.

⏱ ca. 18 Minuten 🎯 Niveau: Fortgeschrittene Grundlagen 🧩 Voraussetzung: Kapitel 5, 8, 10, 22

📋 Was du brauchst

  • Eine n8n-Instanz, lokal oder in der Cloud.
  • Keine API-Credentials: Wir simulieren eine externe API mit Code-Nodes.
  • Grundverständnis für Items, IF und Schleifen.
  • Ein bewusst kleines Testsetup. Performance-Fragen werden mit echten Massen schnell unübersichtlich.
Mehr parallel ist nicht automatisch schneller Ein Workflow kann an API-Limits, Datenbankverbindungen, Speicher, Dateigrößen oder Modellkosten scheitern. Performance heißt daher nicht „alles gleichzeitig“, sondern kontrollierter Durchsatz.
Stand Mai 2026: Code-Nodes und Task Runner Die Beispiele nutzen Code-Nodes, nicht die alten Function-Nodes. In self-hosted Produktivumgebungen werden Code-Nodes über Task Runner ausgeführt; externe Task Runner sind die robustere Betriebsform. Für das lokale Lernsetup musst du daran noch nichts konfigurieren.

Das Ziel

Du baust einen Workflow, der 23 fiktive API-Aufträge in kleinen Gruppen verarbeitet. Der Workflow nutzt Loop Over Items zum Batching, einen simulierten API-Schritt, einen Wait-Node als Bremse und am Ende eine Zusammenfassung. So lernst du das Muster ohne echte Fremddienste und ohne Kosten.

⚡ Performance in einem Satz Miss erst, bremse dann gezielt. Ohne Messpunkt weißt du nicht, ob dein Problem CPU, Speicher, API-Limit, Dateigröße, Netzwerk oder schlechte Workflow-Struktur ist.

Die drei Hebel

HebelWirkungRisiko
Batchgrößebestimmt, wie viele Items pro Runde verarbeitet werdenzu groß: Limits, Speicher, Timeouts
Wartezeitsenkt Anfragefrequenz und glättet Lastzu lang: Workflow dauert unnötig
Fehlerstrategieentscheidet, ob ein Fehler alles stoppt oder markiert wirdzu weich: echte Fehler werden übersehen
Skeptische Einordnung Viele n8n-Nodes verarbeiten mehrere Items automatisch. Ein Loop ist daher nicht der Normalfall. Du nutzt ihn, wenn du eine äußere Grenze brauchst: Rate-Limit, Pagination, Batchgröße, Pause oder kontrollierte Reihenfolge.

Schritt 1 — Workflow anlegen

Wir starten mit einem künstlichen Datenstrom. Das ist didaktisch sauberer als ein echter Dienst, weil du Batchgröße und Fehlerbild kontrollierst.

  1. Neuen Workflow erstellen

    Erstelle einen Workflow und nenne ihn Batching und Rate-Limits lernen.

  2. Manual Trigger hinzufügen

    Füge einen Manual Trigger als ersten Node hinzu.

  3. Code-Node anhängen

    Hänge einen Code-Node an und nenne ihn Demo-Aufträge.

  4. Modus setzen

    Setze den Code-Node auf Run Once for All Items.

  Code · Demo-Aufträge
const jobs = Array.from({ length: 23 }, (_, index) => {
  const id = index + 1;
  return {
    json: {
      job_id: `job-${String(id).padStart(3, '0')}`,
      customer: `Demo-Kunde ${id}`,
      amount_eur: 20 + id * 3,
      priority: id % 7 === 0 ? 'hoch' : 'normal'
    }
  };
});

return jobs;

  1. Node ausführen

    Klicke auf Schritt ausführen. Rechts sollten 23 Items sichtbar sein.

Schritt 2 — Loop Over Items hinzufügen

Der Loop-Node teilt die 23 Items in kleinere Gruppen. Bei Batchgröße 5 entstehen vier volle Batches und ein Rest-Batch mit drei Items.

  1. Loop-Node anhängen

    Ziehe von Demo-Aufträge eine Verbindung ins Leere und suche Loop Over Items.

  2. Batchgröße setzen

    Setze Batch Size auf 5.

  3. Node benennen

    Nenne ihn 5er Batches.

  4. Ausgänge beachten

    Der obere Ausgang verarbeitet den aktuellen Batch. Der Done-Ausgang läuft erst nach allen Batches weiter.

Kein zusätzlicher IF-Node für „alle Items fertig“ Für den Standardfall beendet Loop Over Items die Verarbeitung selbst und nutzt danach den Done-Ausgang. Einen Abbruch-IF brauchst du nur bei selbstgebauten Schleifen, etwa bei unbekannter Pagination.

Schritt 3 — API-Aufruf simulieren

Statt eine echte API aufzurufen, simuliert ein Code-Node eine Antwort. So siehst du, wie aus Roh-Items verarbeitete Items werden.

  1. Code-Node am Loop-Ausgang anhängen

    Verbinde den oberen Ausgang von 5er Batches mit einem neuen Code-Node.

  2. Node benennen

    Nenne ihn API simulieren.

  3. Modus setzen

    Setze den Node auf Run Once for All Items, damit ein Batch gemeinsam verarbeitet wird.

  4. Code einfügen

    Füge diesen Code ein:

  Code · API simulieren
const batch = $input.all();
const batchSize = batch.length;
const now = new Date().toISOString();

return batch.map((item, index) => {
  const job = item.json;
  const simulatedStatus = batchSize > 5 ? 429 : 200;

  return {
    json: {
      ...job,
      batch_size: batchSize,
      batch_position: index + 1,
      api_status: simulatedStatus,
      api_message: simulatedStatus === 200
        ? 'verarbeitet'
        : 'zu viele Anfragen in diesem Batch',
      processed_at: now
    }
  };
});
Warum hier Batchgröße 5? Im Beispiel ist 5 der erlaubte Grenzwert. In der echten Welt liest du diesen Wert in der API-Dokumentation: Anfragen pro Sekunde, pro Minute, pro Tag oder maximale Datengröße pro Anfrage.

Schritt 4 — Wartezeit einbauen

Eine Pause nach jedem Batch senkt die Anfragefrequenz. Das ist das einfachste Muster gegen Rate-Limits: Batch verarbeiten, warten, nächsten Batch holen.

  1. Wait-Node anhängen

    Hänge hinter API simulieren einen Wait-Node.

  2. Node benennen

    Nenne ihn 1 Sekunde warten.

  3. Wartezeit setzen

    Setze die Wartezeit auf 1 second.

  4. Zurück zum Loop verbinden

    Verbinde den Ausgang des Wait-Nodes zurück mit 5er Batches. Dadurch startet die nächste Runde.

  5. Workflow ausführen

    Führe den Workflow aus. Bei 23 Items und Batchgröße 5 siehst du fünf Schleifenrunden.

⚡ Überschlagsrechnung Durchsatz ≈ Batchgröße / Wartezeit. Bei 5 Items und 1 Sekunde Pause sind das grob 5 Items pro Sekunde, ohne Node-Laufzeit mitzuzählen.

Schritt 5 — Zusammenfassung am Done-Ausgang

Die fertigen Items kommen am Done-Ausgang des Loop-Nodes zusammen. Dort ergänzt du eine kleine Auswertung: Anzahl, Statuscodes, Dauerhinweis.

  1. Code-Node am Done-Ausgang anhängen

    Verbinde den unteren Done-Ausgang von 5er Batches mit einem neuen Code-Node.

  2. Node benennen

    Nenne ihn Zusammenfassung.

  3. Modus setzen

    Setze den Node auf Run Once for All Items.

  4. Code einfügen

    Füge diesen Code ein:

  Code · Zusammenfassung
const items = $input.all();

const ok = items.filter((item) => item.json.api_status === 200).length;
const limited = items.filter((item) => item.json.api_status === 429).length;
const batchSizes = [...new Set(items.map((item) => item.json.batch_size))];

return [{
  json: {
    total_items: items.length,
    ok,
    rate_limited: limited,
    batch_sizes_seen: batchSizes,
    recommendation: limited === 0
      ? 'Batchgröße und Wartezeit sind für diesen Test stabil.'
      : 'Batchgröße senken oder Wartezeit erhöhen.'
  }
}];

Schritt 6 — Grenzwert absichtlich brechen

Ein Test ohne Fehlerfall ist zu schwach. Erhöhe die Batchgröße kurz, um zu sehen, ob dein Workflow die simulierte Grenze erkennt.

  1. Batchgröße ändern

    Setze im Loop-Node Batch Size testweise auf 8.

  2. Workflow erneut ausführen

    Starte den Workflow erneut. Der Code-Node API simulieren erzeugt jetzt Status 429.

  3. Zusammenfassung prüfen

    In der Zusammenfassung muss rate_limited größer als 0 sein.

  4. Batchgröße zurücksetzen

    Setze Batch Size wieder auf 5.

429 ist kein „nochmal sofort“ Ein Rate-Limit-Fehler bedeutet fast immer: warten, weniger senden oder API-Regel lesen. Sofortiges Wiederholen kann das Limit verschärfen.

HTTP Request: eingebautes Batching

Wenn du später den echten HTTP Request-Node nutzt, musst du nicht immer Loop und Wait bauen. Der HTTP-Node hat eigene Batching-Optionen. Für einfache API-Listen ist das oft kürzer.

VarianteNutze sie, wenn...Skeptische Frage
HTTP Request mit Batchingein einzelner API-Node gebremst werden sollReicht eine Pause zwischen Requests?
Loop Over Items + Waitmehrere Nodes pro Batch laufen oder die Logik sichtbar sein sollWo ist der Rücksprung, wo ist Done?
Retry On Failkurze, sporadische Fehler abgefangen werden sollenIst Wiederholen erlaubt oder erzeugt es Duplikate?
Queue Modeviele Workflows/Executions parallel betrieben werdenIst die Infrastruktur dafür ausgelegt?
Pragmatische Reihenfolge Erst Node-Einstellungen prüfen. Dann Batchgröße und Wait ergänzen. Erst danach über Queue Mode, Worker und Infrastruktur sprechen. Sonst löst du ein Workflow-Designproblem mit Betriebstechnik.

Execution-Daten klein halten

Performance ist nicht nur Laufzeit. Jede Execution kann Daten speichern. Große JSON-Objekte, PDFs, Bilder oder vollständige API-Antworten machen Debugging bequem, aber Datenbank und Browser schwerfällig.

ProblemGegenmaßnahmeBegründung
riesige API-Antwortfrüh mit Edit Fields oder Code reduzierennur benötigte Felder weitertragen
Binärdaten im WorkflowDateien nicht unnötig durch alle Nodes schleppenSpeicher und Execution-Größe sinken
Debug-Daten bleiben produktiv aktivTestfelder nach dem Aufbau entfernenweniger Rauschen, kleinere Historie
zu viele gespeicherte ExecutionsPruning und Speichereinstellungen prüfenDatenbank bleibt schneller
⚡ Frühes Reduzieren schlägt spätes Aufräumen Wenn ein Workflow 10 MB pro Item durch zehn Nodes trägt, hast du kein Anzeigeproblem. Du hast ein Datenmodellproblem.

✅ Selbsttest

  • Warum brauchst du in n8n nicht für jede Item-Liste einen Loop?
  • Was ist der Unterschied zwischen Loop-Ausgang und Done-Ausgang?
  • Welche zwei Einstellungen reduzierst oder erhöhst du bei Status 429?
  • Warum kann Retry On Fail bei schreibenden Aktionen gefährlich sein?
  • Welche Daten solltest du möglichst früh aus einer großen API-Antwort entfernen?
Antworten 1) Viele Nodes verarbeiten Items automatisch. · 2) Der Loop-Ausgang verarbeitet den aktuellen Batch, Done läuft nach allen Batches weiter. · 3) Batchgröße senken oder Wartezeit erhöhen. · 4) Weil Wiederholungen doppelte Datensätze, Zahlungen oder Nachrichten erzeugen können. · 5) Alles, was spätere Nodes nicht brauchen: Rohtexte, große Arrays, Debugfelder, Binärdaten.
