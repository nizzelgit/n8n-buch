Sub-Workflows & Modularisierung

In diesem Kapitel zerlegst du einen Workflow in zwei Teile: einen Haupt-Workflow und einen Sub-Workflow. Ein Sub-Workflow ist ein kleiner Hilfs-Workflow, den andere Workflows aufrufen können. Der Vorteil: Du musst nichts mehr kopieren. Dieselbe Logik liegt an einer Stelle, und der Aufrufer weiß genau, welche Felder er hineingibt und welche er zurückbekommt.

ca. 18 Minuten Niveau: Fortgeschrittene Grundlagen Voraussetzung: Kapitel 4, 5, 9, 10

Was du brauchst

  • Eine n8n-Instanz, lokal oder in der Cloud.
  • Keine externen Credentials: Das Beispiel arbeitet mit Demo-Daten im Code-Node.
  • Ein Verständnis für Items und JSON-Felder aus Kapitel 5.
  • Etwa 20 Minuten Ruhe, weil du zwei Workflows anlegst und beide testest.
Sub-Workflow ist keine Ausrede für Unklarheit Wenn du Daten nicht sauber übergibst, verschiebst du das Chaos nur in einen zweiten Workflow. Ein guter Sub-Workflow hat einen kleinen Vertrag: Diese Felder kommen rein, diese Felder gehen raus.

Das Ziel

Wir bauen einen kleinen Baustein für Lead-Daten. Ein Lead ist ein Kontakt, der sich für dein Angebot interessiert. Der Haupt-Workflow erzeugt drei Demo-Leads und ruft einen Sub-Workflow auf. Der Sub-Workflow normalisiert Name, E-Mail, Firma und Quelle. Normalisieren heißt: Er bringt die Werte in eine einheitliche Form, zum Beispiel ohne überflüssige Leerzeichen. Dazu berechnet er eine einfache Qualitätsbewertung und gibt das Ergebnis an den Haupt-Workflow zurück. Die Node-Namen, Beschriftungen und Voreinstellungen in diesem Kapitel haben den Stand Juli 2026 und n8n 2.32.x.

80/20-Regel für Modularisierung Erstelle einen Sub-Workflow erst, wenn dieselbe Logik mindestens ein zweites Mal gebraucht wird oder wenn sie im Haupt-Workflow das Verständnis stört. Ein einzelner kurzer Node braucht keine Architektur.

Skeptische Faustregel Ein Sub-Workflow ist gut, wenn du ihn unabhängig testen kannst. Wenn du erst den ganzen Haupt-Workflow starten musst, um den Baustein zu verstehen, ist die Grenze wahrscheinlich falsch gesetzt.

Schritt 1: Sub-Workflow anlegen

Zuerst der wiederverwendbare Teil. Du baust und testest ihn für sich allein; aufgerufen wird er erst später.

  1. Neuen Workflow erstellen

    Lege einen neuen, leeren Workflow an, so wie du es aus den früheren Kapiteln kennst. Nenne ihn Baustein · Lead normalisieren.

  2. Execute Sub-workflow Trigger hinzufügen

    Klicke auf dem leeren Canvas auf Add first step…. Es öffnet sich die Liste What triggers this workflow? („Was startet diesen Workflow?“). Wähle dort When executed by another workflow, also: „wenn ein anderer Workflow ihn ausführt“. Auf dem Canvas heißt der Node danach When Executed by Another Workflow, die n8n-Doku nennt ihn Execute Sub-workflow Trigger. Alle drei Bezeichnungen meinen denselben Node. Der Node öffnet sich direkt, und du siehst seine Einstellungen.

  3. Input data mode prüfen

    Die Einstellung Input data mode legt fest, wie der Baustein seine Eingabedaten annimmt. Sie steht bereits auf Define using fields below: Du zählst die erwarteten Felder einzeln auf. Lass es dabei. Die beiden anderen Modi heißen Define using JSON example für ein Beispiel-JSON und Accept all data für „nimm einfach alles“. Für einen Baustein mit festem Vertrag willst du den ersten Modus.

  4. Vier Eingabefelder anlegen

    Klicke unter Workflow Input Schema viermal auf Add field. Trage als Name nacheinander name, email, company und source ein. Type bleibt bei allen vier auf String, also Text. Du siehst jetzt vier Feldzeilen wie in Abbildung 22.2.

  5. Speichern lassen, Publish merken

    Einen Save-Button suchst du vergeblich. Er ist mit dem Autosave-Update im Januar 2026 (n8n 2.4) verschwunden. n8n speichert seitdem automatisch, laut Doku innerhalb von einer bis fünf Sekunden. Alle Änderungen bleiben aber ein Draft, also ein unveröffentlichter Entwurf, bis du auf Publish klickst. Zum Üben genügt der Draft: Ein manuell gestarteter Haupt-Workflow ruft die Draft-Version des Sub-Workflows auf. Nur produktive Läufe brauchen eine publizierte Version.

Schritt 2: Normalisierung einbauen

Der Sub-Workflow soll alle eingehenden Items bearbeiten. Die Logik bleibt klein und vorhersehbar: Leerzeichen entfernen, E-Mail kleinschreiben, Pflichtfelder prüfen, Score berechnen. Gleiche Eingabe, gleiches Ergebnis.

  1. Code-Node anhängen

    Ziehe vom Trigger eine Verbindung ins Leere und wähle den Code-Node aus.

  2. Node benennen

    Nenne ihn Felder normalisieren.

  3. Modus wählen

    Setze den Modus auf Run Once for All Items. Der Code läuft dann ein einziges Mal und verarbeitet dabei die komplette Item-Liste.

  4. Code einfügen

    Lösche den Beispielcode im Node und füge diesen Code ein:

  Code · Felder normalisieren
const inputItems = $input.all();

function clean(value) {
  return String(value ?? '').trim().replace(/\s+/g, ' ');
}

function normalizeEmail(value) {
  return clean(value).toLowerCase();
}

function emailIsValid(email) {
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
}

return inputItems.map((item) => {
  const input = item.json;
  const name = clean(input.name);
  const email = normalizeEmail(input.email);
  const company = clean(input.company);
  const source = clean(input.source || 'unbekannt').toLowerCase();

  const errors = [];
  if (!name) errors.push('name fehlt');
  if (!email) errors.push('email fehlt');
  if (email && !emailIsValid(email)) errors.push('email ungültig');
  if (!company) errors.push('company fehlt');

  let qualityScore = 0;
  qualityScore += name ? 1 : 0;
  qualityScore += emailIsValid(email) ? 2 : 0;
  qualityScore += company ? 1 : 0;

  return {
    json: {
      ...input,
      name,
      email,
      company,
      source,
      is_valid_email: emailIsValid(email),
      quality_score: qualityScore,
      errors,
      normalized_at: new Date().toISOString()
    }
  };
});
Keine Fehler werfen, wenn der Aufrufer weiterarbeiten soll Für Datenqualität ist es oft besser, Fehler als Daten zurückzugeben: errors, is_valid_email, quality_score. Ein geworfener Fehler stoppt den aufrufenden Workflow.

Schritt 3: Rückgabe sichtbar machen

Der aufrufende Workflow bekommt genau das zurück, was der letzte Node des Sub-Workflows ausgibt. Du könntest den Code-Node also einfach als letzten Node stehen lassen. Ich hänge trotzdem einen eigenen Rückgabe-Node ans Ende: Wer den Workflow in einem halben Jahr öffnet, sieht sofort, wo der Vertrag endet.

Geändert in n8n 2.0: Rückgabe nach einer Wartepause Manche Nodes schicken einen Workflow in den Wartezustand: ein Wait-Node mit mehr als 65 Sekunden Wartezeit, ein Webhook-Aufruf, eine Formulareingabe oder ein Human-in-the-Loop-Node. Enthält dein Sub-Workflow so einen Node, bekommt der Haupt-Workflow seit n8n 2.0 die Daten vom Ende des Sub-Workflows. In n8n 1.x kam an dieser Stelle noch der Input des wartenden Nodes zurück. Erst durch das neue Verhalten kannst du eine Freigabe im Sub-Workflow einholen und das Ergebnis im Haupt-Workflow auswerten. Migrierst du einen alten Workflow, der sich auf das 1.x-Verhalten verlassen hat, musst du ihn umbauen.

  1. Edit-Fields-Node anhängen

    Hänge einen Edit Fields-Node hinter den Code-Node.

  2. Node benennen

    Nenne ihn Rückgabe.

  3. Alle Felder behalten

    Stelle sicher, dass vorhandene Felder nicht gelöscht werden. Der Node ändert hier nichts an den Daten. Er ist nur ein gut lesbarer Endpunkt.

  4. Testdaten manuell ausführen

    Führe den Sub-Workflow mit einem Test-Item aus, zum Beispiel: { "name": " Ada Lovelace ", "email": "ADA@EXAMPLE.COM ", "company": "Analytical Machines", "source": "Webform" }. Die Tabelle unten zeigt dir, was zurückkommen sollte. Stimmt sie mit deiner Ausgabe überein, funktioniert dein Baustein.

FeldErwartete RückgabeWarum wichtig?
nameAda Lovelacekeine doppelten oder äußeren Leerzeichen
emailada@example.comeinheitlich für Abgleich und Deduplizierung

Schritt 4: Sub-Workflow berechtigen

Eine Frage fehlt noch: Wer darf den Baustein überhaupt aufrufen? Das stellst du direkt im Sub-Workflow ein.

  1. Workflow-Einstellungen öffnen

    Klicke im Sub-Workflow oben rechts auf das Options-Menü, also die drei Punkte, und wähle Settings. Ein Fenster mit dem Titel Workflow settings öffnet sich.

  2. Aufrufrechte prüfen

    Suche in dem Fenster die Einstellung This workflow can be called by („Dieser Workflow darf aufgerufen werden von“). Zur Auswahl stehen unter anderem Any workflow, Only workflows in the same project, Selected workflows und No other workflows.

  3. Für das Lernen offen lassen

    Für dieses Kapitel reicht Any workflow in deiner Testumgebung.

  4. Produktiv einschränken

    In produktiven Projekten stellst du auf Selected workflows um und trägst dort genau die Workflows ein, die diesen Baustein aufrufen dürfen.

Aufrufrechte sind keine Formalie Ein Sub-Workflow ist ein internes Werkzeug. Wenn er schreibt, löscht, bezahlt, verschickt oder sensible Daten liest, darf er nicht beliebig aufrufbar sein.

Schritt 5: Haupt-Workflow anlegen

Der Baustein ist fertig. Jetzt baust du den Aufrufer, also den Haupt-Workflow. Er erzeugt drei Demo-Leads, ruft den Baustein auf und verzweigt danach anhand des Feldes is_valid_email.

  1. Neuen Workflow erstellen

    Lege einen zweiten, neuen Workflow an und nenne ihn Lead-Import mit Baustein.

  2. Manual Trigger hinzufügen

    Füge als ersten Node einen Manual Trigger hinzu. Auf dem Canvas beschriftet n8n ihn mit When clicking ‘Execute workflow’.

  3. Code-Node anhängen

    Hänge einen Code-Node an und nenne ihn Demo-Leads.

  4. Modus setzen

    Setze den Code-Node auf Run Once for All Items und füge diesen Code ein:

  Code · Demo-Leads
return [
  {

      name: '  Ada Lovelace ',
      email: 'ADA@EXAMPLE.COM ',

      source: 'Webform'

  },

      name: 'Grace Hopper',

      company: 'Compiler Labs',

    }

  {

      name: '  Katherine Johnson  ',

      company: '',

    }
  }
];

  1. Schritt ausführen

    Klicke im Node auf Execute step. Im Ausgabe-Bereich rechts erscheinen drei Items: Ada, Grace und Katherine. Damit steht dein Testmaterial bereit.

Schritt 6: Sub-Workflow aufrufen

Jetzt verbindest du beide Workflows. Die Brücke ist der Execute-Node: Er nimmt die Items aus dem Haupt-Workflow, übergibt sie an den Baustein und wartet auf die Rückgabe.

  1. Execute Sub-workflow anhängen

    Ziehe vom Node Demo-Leads eine Verbindung ins Leere. Die Node-Suche öffnet sich. Tippe execute sub-workflow ein und wähle den Node Execute Sub-workflow.

  2. Workflow auswählen

    Lass Source auf Database und From list stehen. Wähle in der Liste deinen Baustein Baustein · Lead normalisieren.

  3. Auf Abschluss warten

    Der Haupt-Workflow soll auf das Ergebnis warten. Die zuständige Option heißt Wait For Sub-Workflow Completion und steckt unten im Bereich Options. Sichtbar wird sie erst, wenn du dort auf Add option klickst und sie auswählst. Das musst du hier nicht tun: Sie ist ohnehin eingeschaltet, solange du sie nicht ausdrücklich hinzufügst und abschaltest. Wäre sie aus, könntest du später nicht nach is_valid_email verzweigen.

  4. Alle Items gemeinsam übergeben

    Nutze für dieses Beispiel den Modus Run once with all items. Der Baustein bekommt dann die komplette Liste auf einmal und gibt wieder eine Liste zurück. Den zweiten Modus Run once for each item hat n8n mit 2.30 als deprecated markiert, also als veraltet. Wählst du ihn trotzdem, blendet der Node einen Hinweis ein und empfiehlt stattdessen einen Loop Over Items (Split in Batches)-Node vor dem Execute-Node.

  5. Felder zuordnen

    Unter Workflow Inputs zeigt n8n automatisch die vier Felder an, die dein Baustein erwartet. Ordne jedem Feld den passenden Wert aus den Demo-Leads zu: name = {{$json.name}}, email = {{$json.email}}, company = {{$json.company}}, source = {{$json.source}}.

  6. In die Sub-Ausführung springen

    Führe den Node einmal aus. Danach zeigt er den Link View sub-execution. Ein Klick darauf bringt dich direkt in die Ausführung des Bausteins. Von dort führt ein Link wieder zurück in die Ausführung des Haupt-Workflows. Das ist der schnellste Weg, wenn eine Rückgabe nicht so aussieht wie erwartet.

Der wichtigste Test Dass Items zurückkommen, sagt wenig. Prüfe, ob ein absichtlich kaputtes Item kontrolliert als fehlerhaft markiert wird.

Schritt 7: Nach Rückgabe verzweigen

Jetzt nutzt der Haupt-Workflow das Ergebnis. Gute Leads laufen weiter, fehlerhafte Leads gehen in einen Prüfzweig.

  1. IF-Node anhängen

    Hänge hinter den Execute-Node einen IF-Node und nenne ihn E-Mail gültig?. Ein IF-Node teilt die Items in zwei Ausgänge: True (Bedingung erfüllt) und False (nicht erfüllt).

  2. Bedingung setzen

    Setze die Bedingung auf: is_valid_email ist true.

  3. True-Ausgang beschriften

    Hänge an den True-Ausgang einen No Operation, do nothing-Node und nenne ihn gute Leads. Dieser Node tut nichts. Er ist nur ein Platzhalter mit sprechendem Namen.

  4. False-Ausgang beschriften

    Hänge an den False-Ausgang ebenfalls einen No-Op-Node und nenne ihn prüfen.

  5. Workflow ausführen

    Klicke unten auf dem Canvas auf Execute workflow. Wenn alles stimmt, laufen zwei Items zum True-Ausgang und ein Item, Grace mit der kaputten E-Mail, zum False-Ausgang. Damit funktioniert dein Gespann aus Haupt-Workflow und Baustein.

Score ist nicht Wahrheit Der Score ist nur eine Arbeitsmarkierung. Eine gültige E-Mail beweist nicht, dass die Person existiert oder dass der Lead wertvoll ist. Nutze solche Scores als Filterhilfe, nicht als automatisches Urteil.

Schritt 8: Vertrag dokumentieren

Sub-Workflows werden schnell gefährlich, wenn niemand mehr weiß, welche Felder sie erwarten. Halte den Vertrag deshalb fest: im Workflow-Namen, in Node-Namen oder in einer kurzen Notiz. Für unser Beispiel sieht er so aus:

Teil des VertragsIn diesem Beispiel
Eingabename, email, company, source
Ausgabe zusätzlichis_valid_email, quality_score, errors, normalized_at
FehlerstrategieDatenfehler werden als errors zurückgegeben, nicht geworfen
Seiteneffektkeiner: Der Baustein schreibt nicht in CRM, Slack oder Datenbanken
Geeignete Nutzungvor CRM-Importen, Listenabgleich, Formularverarbeitung
Mathematische Sicht Ein guter Sub-Workflow ist eine Funktion: gleiche Eingabe, gleiche Ausgabe, möglichst wenige Seiteneffekte. Sobald der Baustein gleichzeitig normalisiert, schreibt, benachrichtigt und entscheidet, ist er keine Funktion mehr, sondern ein schwer prüfbarer Prozess.

Schritt 9: Execute-Modi unterscheiden

Zum Schluss ein Überblick über die Aufrufmodi. Der Modus entscheidet, wie Items an den Sub-Workflow übergeben werden. Das wirkt wie eine Kleinigkeit. Er ändert aber, wie lange ein Lauf dauert und wie du einen Fehler später wiederfindest.

ModusWas passiert?Wann sinnvoll?
Run once with all itemsEin Aufruf mit der ganzen Item-ListeBatch-Normalisierung, CSV-Importe, gemeinsame Berechnungen
Run once for each itemEin Aufruf pro Item, seit n8n 2.30 als deprecated markiertnur noch für Altbestand; für Neues nimmst du einen Loop Over Items (Split in Batches)-Node vor dem Execute-Node und bleibst bei Run once with all items
Wait For Sub-Workflow Completion ausHaupt-Workflow läuft weiter, ohne Rückgabe zu nutzenLogging, Benachrichtigung, Hintergrundaufgaben
Fire-and-forget sparsam nutzen Fire-and-forget heißt: aufrufen und nicht auf das Ergebnis warten. Wenn der Haupt-Workflow nicht wartet, darf er keine Entscheidung aus der Rückgabe brauchen. Sonst hängt dein Ergebnis vom zufälligen Timing beider Workflows ab, eine sogenannte Race Condition.

Antworten 1) name, email, company, source. · 2) Weil der Haupt-Workflow dann kontrolliert verzweigen kann. · 3) Wenn die Item-Liste gemeinsam verarbeitet werden soll und ein einzelner Aufruf reicht. · 4) Weil Normalisierung eine reine Funktion bleiben soll; CRM-Schreiben ist ein Seiteneffekt. · 5) Welche Workflows den Baustein aufrufen dürfen und welche Daten sie dadurch verarbeiten.
