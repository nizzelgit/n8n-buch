Sub-Workflows & Modularisierung

In diesem Kapitel zerlegst du einen Workflow in einen Haupt-Workflow und einen wiederverwendbaren Sub-Workflow. Das Ziel ist nicht „mehr Architektur“, sondern weniger Kopieren: gleiche Logik an einer Stelle, klare Eingaben, klare Rückgaben.

⏱ ca. 18 Minuten 🎯 Niveau: Fortgeschrittene Grundlagen 🧩 Voraussetzung: Kapitel 4, 5, 9, 10

📋 Was du brauchst

  • Eine n8n-Instanz, lokal oder in der Cloud.
  • Keine externen Credentials: Das Beispiel arbeitet mit Demo-Daten im Code-Node.
  • Ein Verständnis für Items und JSON-Felder aus Kapitel 5.
  • Etwa 20 Minuten Ruhe, weil du zwei Workflows anlegst und beide testest.
Sub-Workflow ist keine Ausrede für Unklarheit Wenn du Daten nicht sauber übergibst, verschiebst du das Chaos nur in einen zweiten Workflow. Ein guter Sub-Workflow hat einen kleinen Vertrag: Diese Felder kommen rein, diese Felder gehen raus.

Das Ziel

Wir bauen einen kleinen Baustein für Lead-Daten. Der Haupt-Workflow erzeugt drei Demo-Leads und ruft einen Sub-Workflow auf. Der Sub-Workflow normalisiert Name, E-Mail, Firma und Quelle, berechnet eine einfache Qualitätsbewertung und gibt das Ergebnis an den Haupt-Workflow zurück.

⚡ 80/20-Regel für Modularisierung Erstelle einen Sub-Workflow erst, wenn dieselbe Logik mindestens ein zweites Mal gebraucht wird oder wenn sie im Haupt-Workflow das Verständnis stört. Ein einzelner kurzer Node braucht keine Architektur.

Wann lohnt sich ein Sub-Workflow?

Skeptische Faustregel Ein Sub-Workflow ist gut, wenn du ihn unabhängig testen kannst. Wenn du erst den ganzen Haupt-Workflow starten musst, um den Baustein zu verstehen, ist die Grenze wahrscheinlich falsch gesetzt.

Schritt 1 — Sub-Workflow anlegen

Wir beginnen mit dem wiederverwendbaren Teil. Der Sub-Workflow soll später von anderen Workflows aufgerufen werden, aber zunächst testest du ihn isoliert.

  1. Neuen Workflow erstellen

    Erstelle einen neuen Workflow und nenne ihn Baustein · Lead normalisieren.

  2. Execute Sub-workflow Trigger hinzufügen

    Klicke auf Add first step, suche execute sub-workflow trigger und wähle Execute Sub-workflow Trigger.

  3. Eingaben definieren

    Stelle die Eingabe so ein, dass die Felder explizit definiert werden. Lege diese Felder an: name, email, company, source.

  4. Workflow speichern

    Speichere den Workflow. Erst gespeicherte Workflows lassen sich sauber aus dem Haupt-Workflow auswählen.

Schritt 2 — Normalisierung einbauen

Der Sub-Workflow soll alle eingehenden Items bearbeiten. Deshalb bleibt die Logik klein und deterministisch: Leerzeichen entfernen, E-Mail kleinschreiben, Pflichtfelder prüfen, Score berechnen.

  1. Code-Node anhängen

    Hänge hinter den Trigger einen Code-Node.

  2. Node benennen

    Nenne ihn Felder normalisieren.

  3. Modus wählen

    Setze den Modus auf Run Once for All Items. Der Code verarbeitet dann die komplette Item-Liste.

  4. Code einfügen

    Füge diesen Code ein:

  Code · Felder normalisieren
const inputItems = $input.all();

function clean(value) {
  return String(value ?? '').trim().replace(/\s+/g, ' ');
}

function normalizeEmail(value) {
  return clean(value).toLowerCase();
}

function emailIsValid(email) {
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
}

return inputItems.map((item) => {
  const input = item.json;
  const name = clean(input.name);
  const email = normalizeEmail(input.email);
  const company = clean(input.company);
  const source = clean(input.source || 'unbekannt').toLowerCase();

  const errors = [];
  if (!name) errors.push('name fehlt');
  if (!email) errors.push('email fehlt');
  if (email && !emailIsValid(email)) errors.push('email ungültig');
  if (!company) errors.push('company fehlt');

  let qualityScore = 0;
  qualityScore += name ? 1 : 0;
  qualityScore += emailIsValid(email) ? 2 : 0;
  qualityScore += company ? 1 : 0;

  return {
    json: {
      ...input,
      name,
      email,
      company,
      source,
      is_valid_email: emailIsValid(email),
      quality_score: qualityScore,
      errors,
      normalized_at: new Date().toISOString()
    }
  };
});
Keine Fehler werfen, wenn der Aufrufer weiterarbeiten soll Für Datenqualität ist es oft besser, Fehler als Daten zurückzugeben: errors, is_valid_email, quality_score. Ein geworfener Fehler stoppt den aufrufenden Workflow.

Schritt 3 — Rückgabe sichtbar machen

Der aufrufende Workflow erhält die Ausgabe des letzten ausgeführten Nodes im Sub-Workflow. Du könntest den Code-Node direkt als letzten Node lassen. Für Anfänger ist ein eigener Rückgabe-Node aber lesbarer.

  1. Edit-Fields-Node anhängen

    Hänge einen Edit Fields-Node hinter den Code-Node.

  2. Node benennen

    Nenne ihn Rückgabe.

  3. Alle Felder behalten

    Stelle sicher, dass vorhandene Felder nicht gelöscht werden. Der Node dient hier als lesbarer Endpunkt.

  4. Testdaten manuell ausführen

    Führe den Sub-Workflow mit einem Test-Item aus, zum Beispiel: { "name": " Ada Lovelace ", "email": "ADA@EXAMPLE.COM ", "company": "Analytical Machines", "source": "Webform" }.

Schritt 4 — Sub-Workflow berechtigen

Ein Sub-Workflow ist nur dann sinnvoll wiederverwendbar, wenn klar ist, wer ihn aufrufen darf. Das ist eine Betriebsfrage, keine Kosmetik.

  1. Workflow-Einstellungen öffnen

    Öffne im Sub-Workflow die Workflow-Einstellungen.

  2. Aufrufrechte prüfen

    Suche die Einstellung, welche Workflows diesen Workflow aufrufen dürfen.

  3. Für das Lernen offen lassen

    Für dieses Kapitel reicht die allgemeine Aufrufbarkeit in deiner Testumgebung.

  4. Produktiv einschränken

    In produktiven Projekten wählst du gezielt die Workflows aus, die diesen Baustein aufrufen dürfen.

Warum das wichtig ist Ein Sub-Workflow ist ein internes Werkzeug. Wenn er schreibt, löscht, bezahlt, verschickt oder sensible Daten liest, darf er nicht beliebig aufrufbar sein.

Schritt 5 — Haupt-Workflow anlegen

Jetzt baust du den Aufrufer. Er erzeugt drei Leads, ruft den Baustein auf und verzweigt danach nach is_valid_email.

  2. Manual Trigger hinzufügen

  3. Code-Node anhängen

    Hänge einen Code-Node an und nenne ihn Demo-Leads.

  4. Modus setzen

    Setze den Code-Node auf Run Once for All Items.

Schritt 6 — Sub-Workflow aufrufen

Der Execute-Node ist die Brücke. Er nimmt die Items aus dem Haupt-Workflow, übergibt sie an den Baustein und wartet auf die Rückgabe.

  1. Execute Sub-workflow anhängen

    Ziehe vom Node Demo-Leads eine Verbindung ins Leere und suche execute sub-workflow.

  2. Workflow auswählen

    Wähle Baustein · Lead normalisieren.

  3. Auf Abschluss warten

    Lasse die Option aktiv, dass der Haupt-Workflow auf das Ergebnis wartet. Sonst könntest du danach nicht nach is_valid_email verzweigen.

  4. Alle Items gemeinsam übergeben

    Nutze für dieses Beispiel den Modus Run once with all items. So verarbeitet der Baustein die komplette Liste und gibt wieder eine Liste zurück.

  5. Felder zuordnen

    Ordne die vier Eingaben zu: name = {{$json.name}}, email = {{$json.email}}, company = {{$json.company}}, source = {{$json.source}}.

⚡ Der wichtigste Test Prüfe nach dem Execute-Node nicht nur, ob Items zurückkommen. Prüfe, ob ein absichtlich kaputtes Item kontrolliert als fehlerhaft markiert wird.

Schritt 7 — Nach Rückgabe verzweigen

Jetzt nutzt der Haupt-Workflow das Ergebnis. Gute Leads laufen weiter, fehlerhafte Leads gehen in eine Prüfschleife.

  1. IF-Node anhängen

    Hänge hinter den Execute-Node einen IF-Node und nenne ihn E-Mail gültig?.

  2. Bedingung setzen

    Setze die Bedingung auf is_valid_email ist true.

  3. True-Ausgang beschriften

    Hänge an den True-Ausgang zunächst einen No Operation, do nothing-Node und nenne ihn gute Leads.

  4. False-Ausgang beschriften

    Hänge an den False-Ausgang ebenfalls einen No-Op-Node und nenne ihn prüfen.

  5. Workflow ausführen

    Führe den Haupt-Workflow aus. Zwei Items sollten zum True-Ausgang laufen, ein Item zum False-Ausgang.

Score ist nicht Wahrheit Der Score ist nur eine Arbeitsmarkierung. Eine gültige E-Mail beweist nicht, dass die Person existiert oder dass der Lead wertvoll ist. Nutze solche Scores als Filterhilfe, nicht als automatisches Urteil.

Schritt 8 — Vertrag dokumentieren

Sub-Workflows werden schnell gefährlich, wenn niemand mehr weiß, welche Felder erwartet werden. Dokumentiere den Vertrag direkt im Workflow-Namen, in Node-Namen oder in einer kurzen Notiz.

Teil des VertragsIn diesem Beispiel
Eingabename, email, company, source
Ausgabe zusätzlichis_valid_email, quality_score, errors, normalized_at
FehlerstrategieDatenfehler werden als errors zurückgegeben, nicht geworfen
Seiteneffektkeiner: Der Baustein schreibt nicht in CRM, Slack oder Datenbanken
Geeignete Nutzungvor CRM-Importen, Listenabgleich, Formularverarbeitung
Mathematische Sicht Ein guter Sub-Workflow ist eine Funktion: gleiche Eingabe, gleiche Ausgabe, möglichst wenige Seiteneffekte. Sobald der Baustein gleichzeitig normalisiert, schreibt, benachrichtigt und entscheidet, ist er keine Funktion mehr, sondern ein schwer prüfbarer Prozess.

Schritt 9 — Execute-Modi unterscheiden

Der Aufrufmodus entscheidet, wie Items an den Sub-Workflow übergeben werden. Für Anfänger wirkt das klein, aber es verändert Debugging, Performance und Fehlerbild.

ModusWas passiert?Wann sinnvoll?
Run once with all itemsEin Aufruf mit der ganzen Item-ListeBatch-Normalisierung, CSV-Importe, gemeinsame Berechnungen
Run once for each itemEin Aufruf pro Itemisolierte Einzelverarbeitung, wenn ein Itemfehler nicht alle betreffen soll
Wait for completion ausHaupt-Workflow läuft weiter, ohne Rückgabe zu nutzenLogging, Benachrichtigung, Hintergrundaufgaben
Fire-and-forget sparsam nutzen Wenn der Haupt-Workflow nicht wartet, darf er keine Entscheidung aus der Rückgabe brauchen. Sonst baust du eine Race Condition in ein No-Code-Werkzeug ein.

  • Wann ist Run once with all items besser als ein Aufruf pro Item?
