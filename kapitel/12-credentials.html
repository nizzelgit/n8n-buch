Credentials & Authentifizierung

Gmail, Telegram, Sheets, OpenAI: Fast jeder Dienst, den du ansprechen willst, verlangt einen Login. In n8n tippst du Zugangsdaten aber nicht mitten in den Workflow, sondern legst sie als verschlüsselte Credential an. Dieses Kapitel zeigt den Ablauf und danach, was in Team-Instanzen dazukommt.

⏱ ca. 15 Minuten 🎯 Niveau: Einstieg → Mittel 🧩 Voraussetzung: Kapitel 8 (HTTP)

📋 Was du mitbringen solltest

  • Du hast den HTTP-Node gesehen (Kapitel 8) und das Feld „Authentication" bemerkt.
  • Niemals echte Tokens in dieses Buch oder in geteilte Dateien schreiben. Hier stehen nur Platzhalter.

Was eine Credential ist und warum sie getrennt liegt

Eine Credential ist ein gespeichertes Geheimnis: ein API-Schlüssel, ein Token oder ein OAuth-Login. n8n verschlüsselt die Werte und legt sie getrennt vom Workflow in der Datenbank ab. Im Node wählst du nur den Namen der Credential aus. Die Geheimwerte tauchen im Workflow selbst nirgends auf.

Das kannst du sehen. Exportierst du einen Workflow als JSON, steht beim Node nur ein kurzer Block mit der id und dem name der Credential. Der Token steht dort nicht.

Warum getrennt?Konkret
SicherheitBeim Export/Teilen eines Workflows gehen die Geheimnisse nicht mit.
WiederverwendungEine Credential nutzt du in beliebig vielen Nodes und Workflows.
PflegeToken abgelaufen? Einmal zentral ändern, alle Nodes nutzen sofort den neuen.
⚡ Die eine Regel Geheimnisse gehören in Credentials, nie direkt in ein Feld, eine URL oder eine Expression. Wenn du dir aus diesem Kapitel eine einzige Sache merkst, dann diese.

Zwei Wege, sich zu authentifizieren

  • Predefined Credential Type: Kennt n8n den Dienst (Telegram, Google, OpenAI, Slack …), gibt es einen fertigen Typ. Du füllst nur die passenden Felder aus. Wie der Login abläuft, weiß n8n selbst.
  • Generic Credential Type (im HTTP-Node): Für jede beliebige API ohne eigenen Node. Du wählst bei Authentication den Eintrag Generic Credential Type und danach bei Generic Auth Type die Machart: Bearer Auth für ein Authorization: Bearer …, Header Auth für einen eigenen Header-Namen, dazu Basic Auth, Query Auth, Digest Auth, Custom Auth, OAuth1 und OAuth2.

Eine Credential anlegen (Schritt für Schritt)

Am einfachsten legst du sie direkt aus dem Node an, der sie braucht.

  1. Im Node das Credential-Feld öffnen

    Ganz oben in der Parameter-Spalte steht eine Zeile „Credential for …", beim Telegram-Node also „Credential for Telegram API". (In älteren n8n-Versionen hieß dieses Feld „Credential to connect with".) Öffne das Aufklappmenü und klick auf „Create new credential".

  2. Die Felder ausfüllen

    Es öffnet sich ein Formular mit den Feldern, die der Dienst braucht. Bei Telegram ist das im Grunde nur das Access Token vom BotFather; die Base URL steht schon richtig drin.

  3. Speichern (und dabei testen)

    Klick auf „Save". n8n testet die Credential beim Speichern und meldet bei Erfolg in Grün „Connection tested successfully".

  4. Benennen

    n8n benennt die Credential automatisch nach dem Node, hier also Telegram account. Klick oben auf diesen Namen und schreib etwas Sprechenderes hin, z. B. Telegram – Wetter-Bot. So findest du sie später in anderen Nodes wieder.

Es geht auch ohne Node. Über den Create-Knopf oben links im Seitenmenü wählst du Credential und danach den Dienst. Läuft deine Instanz mit Projekten, fragt n8n dabei noch, ob die Credential in deinen persönlichen Bereich oder in ein bestimmtes Projekt gehört.

OAuth: Login per Klick

Manche Dienste (Google, Microsoft …) nutzen OAuth statt eines simplen Tokens. Im Credential-Formular steht dann ein Knopf: bei Google heißt er „Sign in with Google", sonst meist „Connect my account". Ein Klick öffnet das Login-Fenster des Anbieters, du bestätigst den Zugriff, danach speichert n8n den Zugang. Schlüssel kopieren musst du dabei nicht.

Steht die Verbindung, zeigt n8n an dieser Stelle „Account connected". Daneben liegen die Knöpfe „Reconnect", „Switch account" und „Disconnect".

Managed OAuth in der Cloud

Früher war OAuth der unangenehme Teil dieses Kapitels: erst beim Anbieter eine eigene App registrieren, dann Client ID und Client Secret abtippen, dann die Redirect-URL eintragen. Seit n8n 2.11.0 (2. März 2026) übernimmt die n8n Cloud diese App-Registrierung für eine Reihe von Diensten. Beim Anlegen der Credential steht dort einfach ein „Connect"-Knopf: anklicken, beim Dienst anmelden, fertig.

Zum Start dabei waren Slack, HubSpot, GitHub, Google Calendar, PagerDuty, Apify und Firecrawl. Die Release Notes nennen ausdrücklich „and more", die Liste ist also länger. Sieh im Formular selbst nach, ob dein Dienst dabei ist.

Nur in der n8n Cloud Managed OAuth gibt es ausschließlich in der Cloud, weil dort n8n die OAuth-Apps selbst betreibt. Self-hosted registrierst du die App weiterhin von Hand. Und auch in der Cloud bleibst du frei: Im Aufklappmenü für den Auth-Modus stehen „Managed OAuth2 (recommended)" und „Custom OAuth2". Der zweite Eintrag führt zur bekannten manuellen Einrichtung mit eigener Client ID.
Eine Credential, viele Nodes Einmal angelegt, taucht deine Credential in jedem passenden Node im Aufklappmenü auf. Du wählst sie aus, mehr nicht. Die Gesamtliste findest du im linken Menü unter Overview (oder in einem Projekt) im Reiter Credentials.

Eine Credential mit anderen teilen

Arbeitet ihr zu mehreren auf einer Instanz, muss nicht jede Person dasselbe Token neu eintragen. Du gibst deine Credential frei, und die anderen wählen sie in ihren Nodes aus dem Menü.

  1. Zur Credential-Liste gehen

    Im linken Menü Overview anklicken oder ein Projekt, dann Credentials.

  2. Die Credential öffnen

    Klick den Eintrag an, den du freigeben willst.

  3. Auf „Sharing" wechseln

    Das Formular hat oben mehrere Reiter. Klick auf „Sharing".

  4. Person oder Projekt auswählen

    Im Aufklappmenü „Share with projects or users" suchst du den Namen und klickst ihn an.

  5. Speichern

    Auf „Save" klicken. Zum Entziehen gehst du denselben Weg und klickst im Reiter „Sharing" auf das Mülleimer-Symbol neben dem Eintrag.

Wer teilen darf, wer was sieht Teilen kannst du die Credentials, die dir gehören. Liegt eine Credential in einem Projekt, dürfen das nur die Projekt-Admins. Wer eine geteilte Credential benutzt, kann sie weder ansehen noch bearbeiten, sondern nur im Node auswählen. Die Freigabe gibt es in allen Cloud-Plänen und self-hosted ab Business und Enterprise.

Self-hosted: Verschlüsselung und externe Tresore

Weiter oben stand, dass n8n die Werte verschlüsselt. Woher kommt der Schlüssel dafür? Beim allerersten Start würfelt n8n ihn selbst aus und legt ihn im Ordner ~/.n8n ab. Willst du ihn lieber selbst bestimmen, etwa weil du mehrere Instanzen aus demselben Backup betreibst, setzt du vor dem ersten Start die Umgebungsvariable N8N_ENCRYPTION_KEY.

  Terminal
# vor dem ersten n8n-Start setzen, danach nicht mehr ändern
export N8N_ENCRYPTION_KEY=<lange-zufaellige-zeichenkette>
Schlüssel weg, Credentials weg Sichere den Schlüssel zusammen mit der Datenbank. Ohne ihn kommt niemand mehr an die gespeicherten Werte heran, und du legst jede Credential von Hand neu an. Im Queue-Mode brauchen außerdem alle Worker denselben Schlüssel, sonst scheitern dort genau die Ausführungen, die eine Credential benutzen.

Größere Teams halten ihre Geheimnisse oft ohnehin schon in einem Tresor. n8n kann sie von dort holen, statt sie selbst zu speichern. Diese Funktion heißt External Secrets und gehört zu den Enterprise-Plänen. Du gehst auf Settings → External Secrets, klickst „Add secrets vault", vergibst einen Namen und wählst den Anbieter. Zur Auswahl stehen 1Password (über den Connect Server), AWS Secrets Manager, Azure Key Vault, GCP Secrets Manager, HashiCorp Vault und Infisical.

Der Name, den du dem Tresor gibst, ist gleich das erste Stück der Expression, mit der du in einem Credential-Feld an das Geheimnis kommst:

  Expression im Credential-Feld
{{ $secrets.mein_vault.telegram_token }}

1Password ist seit n8n 2.12.0 (9. März 2026) dabei. Dort hat ein Eintrag mehrere Felder, deshalb hängst du das Feld noch hinten an: {{ $secrets.<vault>.<eintrag>.<feld> }}.

Zwei Fallen bei External Secrets

• $secrets löst sich nur in Credential-Feldern auf. Setzt du denselben Ausdruck in einen normalen Node-Parameter, bleibt er wirkungslos, obwohl das Feld Expressions kann.

• Ein Tresor gilt zunächst instanzweit. Seit 2.11.0 lässt er sich auf ein Projekt begrenzen: Settings → External Secrets → Edit, dann unter Share statt Global die Option Project wählen. Danach sehen nur die Credentials dieses Projekts die Geheimnisse.

Sicherheits-Gewohnheiten

  • Geheimnisse nur in Credentials. Nie in URL, Feld oder Expression.
  • Sparsam mit Rechten: Gib einem Token nur die Berechtigungen, die der Workflow wirklich braucht.
  • Regelmäßig erneuern (Rotation) und alte oder ungenutzte Tokens widerrufen.
  • Allowed HTTP Request Domains: Dieses Feld findest du in vielen Credentials für Web-APIs. Es legt fest, gegen welche Domains die Credential im HTTP-Request-Node überhaupt benutzt werden darf. Zur Wahl stehen All, Specific Domains (Kommaliste, z. B. httpbin.org, api.github.com) und None. Im eigenen Node des Dienstes wirkt die Einstellung nicht.
  • Self-hosted: Für Werte, die sich je Umgebung unterscheiden, eignen sich Umgebungsvariablen. Mehr dazu in Kapitel 24.
Wenn etwas schiefgeht

• Fehler 401/403? Token fehlt, ist falsch kopiert (Leerzeichen!) oder abgelaufen. Credential öffnen, Wert neu einsetzen, speichern.

• OAuth-Verbindung abgelaufen? Credential öffnen, auf „Reconnect" klicken und den Login beim Anbieter wiederholen. Gehört die Verbindung jemand anderem, meldet n8n das im Formular: „Only … can edit this connection".

Mini-Übung: eine API mit Header-Token ansprechen

Wir richten im HTTP-Node eine generische Header-Authentifizierung ein (mit Platzhalter-Token).

  1. HTTP-Node, Authentication wählen

    Im HTTP-Node bei Authentication den Eintrag Generic Credential Type wählen. Darunter erscheint das Feld Generic Auth Type; dort Header Auth auswählen.

  2. Credential anlegen

    „Create new credential". Feld Name = Authorization, Feld Value = Bearer DEIN_TOKEN (echtes Token natürlich privat halten).

  3. Speichern & benennen

    Save, Credential z. B. Beispiel-API – Header nennen.

  4. Verwenden

    Zurück im Node ist die Credential ausgewählt. Jeder Request schickt den Header ab jetzt automatisch mit. Du tippst ihn nie wieder ein, und im Workflow steht er auch nicht.

Kürzerer Weg für „Bearer" Erwartet die API genau Authorization: Bearer …, brauchst du Header Auth gar nicht. Nimm bei Generic Auth Type stattdessen Bearer Auth: Dort gibt es nur ein Feld, Bearer Token, und n8n baut den Header selbst zusammen. Header Auth ist die Wahl, wenn der Header anders heißt, etwa X-API-Key.
