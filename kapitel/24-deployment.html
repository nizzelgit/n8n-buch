24 Profi & Betrieb

Deployment, Env-Variablen & Git

In diesem Kapitel lernst du, einen Workflow nicht nur in deiner Testinstanz zum Laufen zu bringen, sondern kontrolliert in eine produktive Umgebung zu übertragen. Der Kern: Workflow-Logik, geheime Zugangsdaten und Umgebungseinstellungen gehören an verschiedene Orte.

⏱ ca. 22 Minuten 🎯 Niveau: Fortgeschrittene Grundlagen 🧩 Voraussetzung: Kapitel 2, 12, 22, 23

📋 Was du brauchst

  • Eine n8n-Testinstanz. n8n Cloud oder eine lokale Self-hosted-Instanz reicht.
  • Grundverständnis für Credentials aus Kapitel 12.
  • Ein Git-Repository, wenn du den Git-Teil praktisch nachvollziehen willst.
  • Keine echten API-Schlüssel. Dieses Kapitel nutzt Platzhalter und Demo-Werte.
Deployment ist kein Kopieren mit Hoffnung Wenn ein Workflow nur funktioniert, weil ein Token hart im HTTP-Node steht oder weil die Webhook-URL zufällig passt, ist er nicht deploybar. Er funktioniert nur zufällig in genau dieser Umgebung.

Das Ziel

Du baust kein vollständiges Server-Setup. Du lernst das Betriebsmodell: Eine Entwicklungsinstanz enthält die Workflow-Logik, Git hält die nachvollziehbare Version, und Produktion bekommt eigene Credentials und eigene Umgebungswerte. Damit wird ein Workflow zwischen Test und Produktion prüfbar.

⚡ 80/20-Regel für Deployment Versioniere die Logik, nicht die Geheimnisse. Prüfe Webhook-URL, Credentials und Umgebungswerte getrennt. Mehr Betriebstechnik brauchst du erst, wenn diese drei Dinge sauber sind.

Skeptische Einordnung Git löst nicht alle Betriebsfragen. Git beantwortet nur: Welche Workflow-Version ist gemeint? Ob die Instanz richtig konfiguriert, erreichbar und berechtigt ist, bleibt eine separate Prüfung.

Schritt 1 — Umgebungen benennen

Ein Deployment wird unklar, wenn du nur „meine n8n-Instanz“ sagst. Du brauchst mindestens zwei Rollen: Entwicklung und Produktion. Das kann am Anfang auch dieselbe Maschine mit zwei getrennten Workflows sein.

  1. Entwicklungsumgebung festlegen

    Nenne sie eindeutig dev. Dort darfst du Nodes testen, Daten verfälschen und Fehler erzeugen.

  2. Produktionsumgebung festlegen

    Nenne sie eindeutig prod. Dort laufen echte Trigger, echte Empfänger und echte Nebenwirkungen.

  3. Workflow-Namen trennen

    Nutze Namen wie dev · Lead-Routing und prod · Lead-Routing, solange du keine echte Umgebungstrennung hast.

  4. Nebenwirkungen markieren

    Schreibende Nodes wie CRM-Update, E-Mail, Slack oder Zahlung bekommen im Namen einen klaren Hinweis: CRM schreiben, E-Mail senden, Ticket anlegen.

UmgebungDarf kaputtgehen?Darf echte Daten schreiben?Typische Trigger
devjaneinManual Trigger, Test-Webhook
prodneinja, bewusstSchedule, Webhook, App-Trigger
Ein Workflow mit Umschalter ist selten sauberer Ein Feld mode = prod im Workflow wirkt bequem. Es macht aber Tests riskant, weil eine falsche Einstellung echte Nachrichten oder Datensätze erzeugen kann. Trenne Umgebungen lieber sichtbar.

Schritt 2 — Secrets aus der Logik entfernen

Secrets gehören in n8n-Credentials oder in die Umgebungsverwaltung deiner Instanz. Nicht in Code-Nodes, nicht in HTTP-Header-Felder als Klartext und nicht in Git.

  1. HTTP-Node prüfen

    Öffne einen Workflow mit einem HTTP Request-Node.

  2. Authentication verwenden

    Stelle Authentication auf die passende Methode: API Key, Bearer Token, OAuth2 oder Header Auth.

  3. Credential anlegen

    Lege ein Credential mit einem neutralen Namen an, zum Beispiel CRM API · dev.

  4. Produktions-Credential separat anlegen

    In Produktion legst du später CRM API · prod an. Es darf denselben Workflow nutzen, aber nicht denselben geheimen Schlüssel.

Variablen sind keine Credentials n8n-Variablen sind gut für nicht-geheime Werte wie CRM_BASE_URL, REPORT_CHANNEL oder ENV_NAME. API-Schlüssel und Tokens bleiben Credentials. Wenn deine n8n-Version oder dein Plan keine Variablen-Funktion anbietet, nutze pro Umgebung einen kleinen Konfiguration-Node, aber auch dort keine Secrets.

Schritt 3 — Self-hosting minimal konfigurieren

Wenn du n8n selbst hostest, kommen mehrere Betriebswerte aus Umgebungsvariablen. Das folgende Beispiel ist bewusst ein Lern-Skelett. Es ersetzt kein gehärtetes Server-Setup, zeigt aber die entscheidenden Stellen.

N8N_ENCRYPTION_KEY ist kritisch Dieser Schlüssel schützt gespeicherte Credentials. Wenn du ihn verlierst oder zwischen Instanzen unbedacht änderst, können Credentials unbrauchbar werden. Sichere ihn getrennt von Git, wie ein echtes Secret.

Schritt 4 — Webhook-URL prüfen

Viele Deployment-Fehler zeigen sich zuerst bei Webhooks. Intern läuft n8n vielleicht auf Port 5678, extern muss aber eine stabile HTTPS-Adresse erreichbar sein.

  1. Test-Webhook anlegen

    Erstelle einen neuen Workflow mit Webhook Trigger und nenne ihn dev · Webhook-URL prüfen.

  2. Pfad setzen

    Setze den Pfad auf deployment-test.

  3. Test-URL öffnen

    Starte den Testmodus und öffne die angezeigte Test-URL im Browser.

  4. Produktions-URL prüfen

    Aktiviere den Workflow kurz in einer Testumgebung und prüfe, ob die Produktions-URL die richtige Domain zeigt.

  5. Falsche Domain korrigieren

    Wenn n8n eine interne Adresse oder localhost anzeigt, korrigiere WEBHOOK_URL und die externe Editor-URL der Instanz.

Schritt 5 — Git-Strategie wählen

n8n kann Workflow-Versionen je nach Edition und Plan direkt mit Git verbinden. Wenn diese Funktion in deiner Umgebung nicht verfügbar ist, ist der Workaround einfach: Workflow-JSON exportieren und sauber in Git ablegen.

VarianteGeeignet fürRisiko
n8n Source ControlTeams mit passender n8n-Edition, Review-Prozess und mehreren Umgebungenmuss sauber eingerichtet und verstanden werden
Manueller JSON-ExportEinzelpersonen, Lernprojekte, kleine Teams ohne Source-Control-FunktionImport/Export kann vergessen werden
Gar kein Gitnur schnelle Wegwerf-Testskeine nachvollziehbare Version, schlechte Wiederherstellung
⚡ Pragmatische Empfehlung Wenn Source Control verfügbar ist: nutze es. Wenn nicht: exportiere jede stabile Workflow-Version als JSON in ein Git-Repository. Das ist weniger elegant, aber deutlich besser als gar keine Historie.

Schritt 6 — Source Control in n8n nutzen

Falls deine n8n-Edition Source Control unterstützt, läuft der Ablauf grob so: Git-Zugang verbinden, Änderungen aus der Entwicklungsinstanz pushen, in Produktion pullen und danach erst aktivieren.

  1. Einstellungen öffnen

    Öffne in n8n die Einstellungen und suche den Bereich Source Control.

  2. Repository verbinden

    Verbinde ein Git-Repository über die angebotene Authentifizierung. Nutze ein separates Repo oder einen klar getrennten Ordner für n8n-Workflows.

  3. Entwicklungsänderung pushen

    Push aus dev nur dann, wenn der Workflow gespeichert, getestet und verständlich benannt ist.

  4. Produktionsinstanz pullen

    Ziehe die Änderung in prod. Prüfe danach Credentials und Variablen, bevor du aktivierst.

  5. Aktivierung bewusst durchführen

    Aktiviere den Workflow erst nach einem Testlauf mit ungefährlichen Daten.

Source Control ersetzt keine Freigabe Ein Pull in Produktion ist noch kein erfolgreiches Deployment. Erst wenn Credentials, Webhook-URL, Variablen und Testlauf stimmen, ist die Änderung betriebsbereit.

Workaround: JSON-Export in Git

Wenn du keine eingebaute Source-Control-Funktion hast, nutze eine einfache Ordnerstruktur. Wichtig ist nicht die Perfektion, sondern die Wiederholbarkeit.

  Repository-Struktur
n8n-workflows/
├── README.md
├── workflows/
│   ├── lead-routing.json
│   ├── news-aggregator.json
│   └── invoice-extraction.json
├── docs/
│   └── deployment-checklist.md
└── .gitignore

  1. Workflow exportieren

    Öffne den Workflow, wähle Download oder Export und speichere die JSON-Datei unter einem sprechenden Namen.

  2. JSON prüfen

    Öffne die Datei und suche nach echten Tokens, Passwörtern oder Kundendaten. Wenn du welche findest: nicht committen, sondern zuerst den Workflow bereinigen.

  3. Commit schreiben

    Committe die Änderung mit einer knappen fachlichen Beschreibung, zum Beispiel Lead-Routing um Fehlerzweig ergänzt.

  4. In Produktion importieren

    Importiere die JSON-Datei in die Produktionsinstanz. Danach Credentials auswählen, Variablen prüfen und Testlauf durchführen.
