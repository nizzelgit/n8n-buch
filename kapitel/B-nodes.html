Spickzettel: die wichtigsten Nodes

n8n hat viele Nodes. Du brauchst am Anfang nicht alle. Dieser Spickzettel ordnet die wichtigsten Nodes danach, welches Problem sie lösen: starten, Daten holen, Daten verändern, verzweigen, antworten und stoppen. Dazu die KI-Nodes, der Node für die gesparte Zeit und die Namen, die n8n unterwegs geändert hat.

⏱ ca. 12 Minuten 🎯 Niveau: Nachschlagen 🧩 Voraussetzung: Kapitel 5
80/20 für Nodes Die meisten Einsteiger-Workflows entstehen aus zehn Nodes: Manual Trigger, Schedule Trigger, Webhook, HTTP Request, Edit Fields (Set), If, Switch, Merge, Code und Respond to Webhook.
Welche Namen hier stehen Die Namen in diesem Spickzettel sind die Anzeigenamen aus dem Node-Panel, Stand Juli 2026 und n8n 2.32.x. Manche sind dort länger als auf dem Canvas. Du suchst nach „Edit Fields (Set)“, auf dem Canvas steht danach kurz „Edit Fields“. Genauso bei „Loop Over Items (Split in Batches)“. Die Suche im Node-Panel reagiert auf beide Teile: edit fields findet den Node, set genauso.

Diese Nodes suchst du vergeblich n8n 2.0 hat aufgeräumt. Den Start-Node gibt es nicht mehr. Für Testläufe nimmst du jetzt den Manual Trigger, in aufgerufenen Workflows den Execute Sub-workflow Trigger. Ebenfalls entfernt sind die Nodes für Dienste, die es selbst nicht mehr gibt: Spontit, crowd.dev, Kitemaker und Automizy. In diesem Spickzettel steht keiner davon. Wenn du aber einen älteren Workflow oder eine ältere Anleitung aus dem Netz öffnest, ist das oft die Ursache für einen Node, den n8n nicht mehr kennt.

HTTP Request kann alles, ist aber selten der erste Griff Wenn ein Dienst einen eigenen n8n-Node hat, ist dieser meist schneller verständlich: Er führt dich durch Authentifizierung, Ressourcen und Felder. Zum HTTP Request greifst du, wenn es keinen passenden Node gibt oder der vorhandene Node die eine Operation nicht kennt, die du brauchst.
Zwei Stolperstellen an diesen Nodes Seit n8n 2.0 darf „Read/Write Files from Disk“ selbst gehostet nur noch unter ~/.n8n-files lesen und schreiben. Das steckt in der Variable N8N_RESTRICT_FILE_ACCESS_TO. Brauchst du einen anderen Ordner, trägst du ihn dort ein, mehrere Ordner trennst du mit Semikolon. Der Notion-Node wiederum läuft inzwischen in Version 3. Neben Database gibt es dort die Ressource Data Source mit Get und Search, weil Notion seine Datenbanken in Data Sources aufgeteilt hat. Der Notion Trigger fragt ab seiner Node-Version 1.1 ebenfalls nach einer Data Source statt nach einer Database.

Zeitersparnis messen

Wie viel Arbeit spart ein Workflow eigentlich? Seit n8n 2.1.0 gibt es dafür einen eigenen Node. Im Node-Panel heißt er Track Time Saved, auf dem Canvas trägt er danach den kurzen Namen Time Saved. Er reicht alle Items unverändert weiter und meldet nebenbei, wie viele Minuten dieser Lauf gespart hat.

  1. Workflow-Einstellungen öffnen

    Klicke im Workflow oben rechts auf das Drei-Punkte-Menü und wähle Settings.

  2. Berechnung umstellen

    Setze Estimated time saved auf Dynamic und speichere. Die Alternative Fixed ist eine feste Minutenzahl pro Ausführung, dafür brauchst du keinen Node.

  3. Node einsetzen

    Hänge in jeden Zweig, der wirklich Arbeit spart, einen Track Time Saved-Node.

  4. Minuten eintragen

    Der Node hat zwei Felder. Calculation Mode steht auf Once For All Items oder Per Item, wobei Per Item die Minuten mit der Anzahl der Eingabe-Items multipliziert. In Minutes Saved trägst du die Zahl ein.

n8n addiert die Werte aller Time-Saved-Nodes, die in einem Lauf tatsächlich durchlaufen werden. Die Summe landet im Insights-Banner oben im Bereich Overview; das ausführliche Insights-Dashboard gibt es erst ab dem Pro-Plan. Zwei Grenzen solltest du kennen. Insights zählt nur Produktions-Ausführungen, deine Testläufe im Editor also nicht. Und gezählt wird nur der Eltern-Workflow: Zeit aus Sub-Workflows rechnet n8n bisher nicht mit.

KI-Bausteine

Diese Nodes gehören zu den Kapiteln 17, 20 und 21. Sie funktionieren anders als der Rest: Ein Chat Model, ein Memory oder ein Tool wird nicht in die Kette gehängt, sondern von unten an einen Root-Node angedockt. n8n nennt das Cluster Nodes, der angedockte Teil heißt Sub-Node.

Simple Memoryder Agent sich an die vorigen Nachrichten erinnern sollLäuft die Instanz im Queue-Mode? Dann Redis oder Postgres.

Bei Memory und Vector Store lohnt ein Blick über die Tabelle hinaus. Der Memory-Sub-Node Motorhead ist seit n8n 2.8.0 deprecated, weil das Projekt dahinter nicht mehr gepflegt wird. Im Node-Panel taucht er nicht mehr auf, bestehende Workflows laufen weiter. Für alles jenseits des Lernbeispiels nimmst du ohnehin Redis Chat Memory oder Postgres Chat Memory. Der Simple Vector Store hat ein anderes Problem: Er hält die Vektoren im Arbeitsspeicher der Instanz, ein Neustart löscht sie. Abgekündigt ist er nicht. Produktiv nimmst du trotzdem Pinecone Vector Store, Qdrant Vector Store oder PGVector Vector Store.

Ein Agent ist die teurere Antwort Ein AI Agent ruft das Modell mehrfach auf, bis er fertig ist. Wenn die Aufgabe immer gleich abläuft, ist die Basic LLM Chain billiger und leichter zu debuggen. Nimm den Agent erst, wenn der Ablauf wirklich von der Eingabe abhängt.

Auswahlregel

  1. Start klären

    Kommt das Ereignis per Zeitplan, Webhook, Formular, manuell oder aus einem Dienst?

  2. Datenquelle bestimmen

    Gibt es einen passenden App-Node? Wenn nicht, prüfe HTTP Request.

  3. Transformation klein halten

    Nutze Edit Fields (Set), Filter, Sort und Limit, bevor du Code einsetzt.

  4. Verzweigung sichtbar machen

    Nimm If für zwei Wege, Switch für mehrere Wege.

  5. Schreibende Nodes absichern

    Prüfe Dubletten, Testdaten und Credentials, bevor Daten extern verändert werden.
