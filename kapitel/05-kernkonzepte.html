Kernkonzepte: Nodes, Items & Datenfluss

Wenn ein einziges Kapitel dieses Buchs darüber entscheidet, ob du n8n wirklich verstehst, dann dieses. Hier klären wir, was genau zwischen den Nodes hin- und herfließt und wie du darauf zugreifst.

⏱ ca. 24 Minuten 🎯 Niveau: Einstieg → Mittel 🧩 Voraussetzung: Kapitel 4 (erster Workflow)

Die eine Sache, die alles erklärt: das Item

Zwischen zwei Nodes fließen keine „Texte“ oder „Zahlen“, sondern Items. Ein Item ist ein kleines Datenpaket. Und ganz wichtig:

⚡ Die goldene Regel Ein Node bekommt immer eine Liste von Items herein und gibt eine Liste von Items heraus. Auch wenn es nur ein einziges Item ist, ist es technisch eine Liste mit einem Eintrag. Verinnerliche das, und n8n wird durchschaubar.

Jedes Item hat zwei Fächer:

  • json – die eigentlichen Daten als JSON-Objekt (Felder mit Werten). 95 % der Zeit arbeitest du hiermit.
  • binary – optionale Dateianhänge (Bild, PDF, …). Brauchst du erst bei Datei-Workflows.

Technisch sieht ein Datenpaket zwischen zwei Nodes also so aus: eine Liste, darin Objekte mit dem Schlüssel json und optional dem Schlüssel binary. Unter binary liegt jede Datei unter einem eigenen Namen, mit den Feldern data (Base64), mimeType, fileExtension und fileName. Nur data ist Pflicht.

  Der Aufbau eines Items
[
  {
    "json": { /* deine Daten */ },
    "binary": {
      "rechnung": {
        "data":          "JVBERi0xLjQK…",   // Base64, Pflicht
        "mimeType":      "application/pdf",
        "fileExtension": "pdf",
        "fileName":      "rechnung.pdf"
      }
    }
  }
]
Wo liegen Binärdaten wirklich? Die Base64-Zeichenkette oben ist die Sicht des Workflows auf die Datei. Wo die Bytes tatsächlich liegen, regelt die Umgebungsvariable N8N_DEFAULT_BINARY_DATA_MODE. Seit n8n 2.0 landen sie nie mehr einfach im Arbeitsspeicher: im Normalbetrieb im Dateisystem, im Queue-Modus in der Datenbank, auf Wunsch in einem S3-kompatiblen Speicher. Der alte Wert default, der die Bytes während der Ausführung im Speicher hielt, ist mit 2.0 weggefallen. Falls du ihn noch in einer .env-Datei stehen hast, wirf ihn raus. An der Struktur des Items ändert das nichts. An deinem Speicherverbrauch schon: Eine 80 MB große PDF-Datei bringt dir die Instanz jetzt nicht mehr so leicht zum Absturz.

Wie Items in der Oberfläche aussehen

n8n zeigt dieselben Items in drei Ansichten an. Du wählst sie über die Reiter Tabelle / JSON / Schema im Eingangs- und Ausgangspanel. Darunter liegen immer dieselben Daten, nur anders dargestellt:

⚡ Tabelle zum Überblicken, JSON zum Verstehen, Schema zum Verdrahten

Beim Bauen hilft dir die Schema-Ansicht am meisten. Du siehst dort die Feldnamen und kannst sie per Drag-and-drop in ein Expression-Feld ziehen, statt sie abzutippen.

Ein Detail, über das viele stolpern: Tabelle und JSON zeigen alle Items, das Schema baut n8n dagegen nur aus dem ersten Item. Ein Feld, das erst im dritten Item auftaucht, fehlt dort. Wenn du ein Feld vermisst, schau zur Kontrolle in die JSON-Ansicht.

JSON in 3 Minuten (für alle, die unsicher sind)

JSON ist nur eine Schreibweise für strukturierte Daten. Du musst es nicht schreiben können, aber lesen schon. Es gibt genau diese Bausteine:

  Die JSON-Bausteine
{
  "text":    "in Anführungszeichen",   // String (Text)
  "zahl":    42,                  // Number
  "wahr":    true,                // Boolean (true/false)
  "leer":    null,                // nichts
  "liste":   [1, 2, 3],           // Array (geordnete Liste)
  "objekt":  {                       // verschachteltes Objekt
    "stadt": "Berlin"
  }
}

Das Wichtigste ist die Verschachtelung: Objekte können in Objekten stecken. Um an Berlin heranzukommen, schreibst du den Pfad mit Punkten: objekt.stadt. Genau das machst du in Expressions ständig.

Der Zugriff: Expressions & $json

Eine Expression ist ein kleines Stück Code in doppelten geschweiften Klammern, das n8n beim Ausführen durch den echten Wert ersetzt. Die wichtigste Variable darin ist $json:

ExpressionBedeutung / Ergebnis
{{ $json.name }}Das Feld name des aktuellen Items → „Anna“
{{ $json.current.temperature_2m }}Verschachtelt: in current das Feld temperature_2m
{{ $json.liste[0] }}Das erste Element einer Liste (Zählung beginnt bei 0!)
{{ $json.alter + 1 }}Rechnen geht auch → 30
{{ $json.name.toUpperCase() }}Funktionen anwenden → „ANNA“
{{ $now }}Aktuelles Datum mit Uhrzeit, in der Zeitzone des Workflows
Woher weiß ich die Feldnamen? Aus dem Eingangspanel des Nodes (Schema-Ansicht). n8n zeigt dir dort genau die Felder, die gerade ankommen. Du musst nichts raten. Zieh die Felder per Drag-and-drop direkt ins Eingabefeld.

Auf andere Nodes zugreifen: $('Node-Name')

$json meint immer das json-Fach des Items, das gerade in den Node hineinläuft, also das Ergebnis des direkt vorherigen Nodes. Manchmal brauchst du einen Wert von weiter vorn in der Kette, etwa die ursprüngliche E-Mail aus dem Trigger, wenn schon drei Nodes dazwischenliegen. Dafür gibt es:

  Zugriff auf einen benannten Node
// Hol das Feld "email" aus dem Node namens "Webhook"
{{ $('Webhook').item.json.email }}
⚡ Die zwei Zugriffe, die du wirklich brauchst

$json.feld → Wert aus dem vorherigen Node.

$('Name').item.json.feld → Wert aus einem beliebigen früheren Node.

Mit diesen beiden verdrahtest du gefühlt jeden Workflow.

Ein Item oder viele? Das „läuft pro Item“-Prinzip

Hier passiert der häufigste Aha-Moment. Bekommt ein Node mehrere Items, führt er seine Aktion für jedes Item einzeln aus. Drei Items rein → Aktion läuft dreimal → drei Items raus.

Ausnahmen gibt es. Summarize, Aggregate und Merge fassen mehrere Items zu weniger Items zusammen. Alle anderen Nodes arbeiten die Liste stumpf von oben nach unten durch. Was das Zusammenfassen für deine Expressions bedeutet, siehst du gleich im nächsten Abschnitt.

⚡ Du brauchst keine Schleife Willst du „für jede Zeile in der Tabelle eine Nachricht“, sorgst du dafür, dass jede Zeile ein eigenes Item ist. Den Rest macht n8n von allein, indem es den Node pro Item wiederholt. Kein for, kein Zähler.

Woher .item weiß, welches Item gemeint ist (Item-Linking)

Jetzt, wo klar ist, dass ein Node dieselbe Aktion 50-mal ausführen kann, stellt sich eine Frage: Welchen der 50 Webhook-Datensätze meint eigentlich $('Webhook').item? Genau den, aus dem das Item entstanden ist, das der Node gerade bearbeitet. Dafür hängt n8n an jedes Ausgabe-Item eine Notiz, aus welchem Eingabe-Item es hervorgegangen ist. Diese Notiz heißt paired item, das Verfahren heißt Item-Linking. Bei gleich vielen Ein- und Ausgabe-Items verknüpft n8n der Reihe nach: Ausgabe 1 zu Eingabe 1, Ausgabe 2 zu Eingabe 2, und so fort.

Meistens merkst du davon nichts. Auffallen wird es dir an dem Tag, an dem eine Expression mit einer dieser beiden Meldungen abbricht:

MeldungUrsacheWas hilft
Multiple matching items for expression Mehrere Items wurden zu einem zusammengefasst, typisch nach Summarize, Aggregate oder Merge. Die Zuordnung ist nicht mehr eindeutig. Statt .item genauer werden: .first(), .last() oder .all()[0]. Oder einen anderen Node ansprechen, der denselben Wert eindeutig führt.
Info for expression missing from previous node Ein Node in der Kette liefert die Paarungs-Notiz gar nicht mit. Das passiert bei Code-Nodes, die Items selbst zusammenbauen, und bei manchen Community-Nodes. Im Code-Node die Paarung mitgeben (pairedItem). Bei fremden Nodes bleibt der Umweg über .first() oder .all(), weil beide ohne Paarungs-Notiz auskommen.

Daten „festpinnen“ zum Testen (Pinning)

Beim Entwickeln willst du nicht bei jedem Test echte E-Mails verschicken oder eine API hundertmal aufrufen. Lösung: Pin data. Du führst einen Node einmal aus und pinnst sein Ergebnis fest. Bei den nächsten Tests nimmt n8n diese gespeicherten Daten, statt neu abzurufen. Ein angepinnter Node bekommt ein 📌-Symbol, und im Ausgangspanel steht das Banner „This data is pinned“. Über den Link „Unpin“ darin holst du beim nächsten Lauf wieder frische Daten.

1 Node ausführen → 2 im Ausgangspanel auf 📌 „Pin data“ klicken → 3 ab jetzt fixe Testdaten
Drei Grenzen, die du kennen solltest Pinnen geht nur bei Nodes mit einem einzigen Hauptausgang. Enthält der Ausgang Binärdaten, geht es gar nicht. Und gepinnte Daten gelten ausschließlich beim Entwickeln: Läuft der Workflow produktiv, ignoriert n8n sie und ruft die echte Quelle ab. Wer das vergisst, wundert sich später über Testdaten, die im Live-Betrieb plötzlich nicht mehr auftauchen.

Wie das alles zusammenspielt: ein Durchlauf

Fügen wir das Wissen zusammen. So „denkt“ n8n, wenn du unten am Canvas auf „Execute workflow“ klickst (in älteren Versionen hieß der Knopf „Test workflow“):

  1. Trigger erzeugt das/die Start-Item(s)

    Beim manuellen Trigger ist das ein leeres Item, bei „Sheets lesen“ z. B. eine Zeile pro Item.

  2. Items wandern in den nächsten Node

    Der nimmt sie als Eingang (linkes Panel).

  3. Der Node arbeitet, Item für Item

    Er wendet seine Einstellungen an; Expressions werden jetzt zu echten Werten ausgewertet.

  4. Er gibt neue Items aus

    Diese erscheinen im Ausgang (rechtes Panel) und sind der Eingang des nächsten Nodes.

  5. … und so weiter bis zum Ende

    Bis kein Node mehr folgt. Jeder Schritt ist in den Ausführungen nachvollziehbar.

✅ Selbsttest: verstehst du den Kern?

  • Was ist der Unterschied zwischen $json und $('Trigger').item.json?
  • Du hast 5 Items im Eingang eines „Slack senden“-Nodes. Wie viele Nachrichten gehen raus?
  • Welche Ansicht (Tabelle/JSON/Schema) nutzt du, um die Feldnamen mit ihren Typen zu sehen? Und warum reicht sie nicht immer?
  • Wozu pinnst du Daten?
  • Warum kann $('Webhook').item hinter einem Merge-Node scheitern?
Antworten 1) $json = vorheriger Node, $('Trigger')… = ein bestimmter, beliebiger Node. · 2) Fünf, der Node läuft pro Item. · 3) Schema. Sie zeigt aber nur die Felder des ersten Items, für den vollen Datensatz musst du in JSON oder Tabelle schauen. · 4) Um beim Testen keine echten Aktionen auszulösen und APIs zu schonen. · 5) Merge fasst mehrere Eingabe-Items zu einem Ausgabe-Item zusammen, die Paarung ist dann nicht mehr eindeutig. Nimm .first(), .last() oder .all()[0].

Das mentale Modell steht. Bevor du weiterliest, spiel den Item-Linking-Fall ruhig einmal selbst durch: Führe zwei Zweige über einen Merge-Node zusammen und greif in einem Node dahinter mit {{ $('Webhook').item.json.email }} auf den Anfang zurück. Kommt eine der beiden Meldungen aus der Tabelle, weißt du jetzt, woran es liegt. Im nächsten Kapitel gehen wir tiefer in Expressions, mit Datumsrechnen, zusammengesetzten Texten und Bedingungen. Damit bringst du Daten in genau die Form, die der nächste Node braucht.
