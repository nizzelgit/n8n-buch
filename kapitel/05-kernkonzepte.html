Kernkonzepte: Nodes, Items & Datenfluss

Dieses Kapitel ist das wichtigste im ganzen Buch. Hier lernst du, was genau zwischen den Nodes fließt und wie du an diese Daten herankommst. Lies es in Ruhe, alles Weitere baut darauf auf.

ca. 24 Minuten Niveau: Einstieg → Mittel Voraussetzung: Kapitel 4 (erster Workflow)

Die eine Sache, die alles erklärt: das Item

Zwischen zwei Nodes fließen keine losen „Texte“ oder „Zahlen“. Es fließen Items. Ein Item ist ein kleines Datenpaket, zum Beispiel ein Kontakt, eine E-Mail oder eine Tabellenzeile. Und ganz wichtig:

Die goldene Regel Ein Node bekommt immer eine Liste von Items herein und gibt eine Liste von Items heraus. Auch wenn es nur ein einziges Item ist, ist es technisch eine Liste mit einem Eintrag. Verinnerliche das, und n8n wird durchschaubar.

Jedes Item hat zwei Fächer:

  • json – die eigentlichen Daten: Felder mit Werten, z. B. name: "Anna". Die Schreibweise dafür heißt JSON, dazu gleich mehr. 95 % der Zeit arbeitest du mit diesem Fach.
  • binary – optionale Dateianhänge (Bild, PDF, …). Das brauchst du erst bei Datei-Workflows.

So sieht ein Item von innen aus. Du musst das nicht auswendig lernen, nur einmal gesehen haben. Die eckigen Klammern außen sind die Liste aus der goldenen Regel. Darin steckt das Item als Objekt mit dem Schlüssel json und optional dem Schlüssel binary. Unter binary bekommt jede Datei einen eigenen Namen (hier „rechnung“). Darin gibt es die Felder data, mimeType, fileExtension und fileName. Nur data ist Pflicht: der Dateiinhalt als Base64, also als lange Buchstabenkette codiert.

  Der Aufbau eines Items
[
  {
    "json": { /* deine Daten */ },
    "binary": {
      "rechnung": {
        "data":          "JVBERi0xLjQK…",   // Base64, Pflicht
        "mimeType":      "application/pdf",
        "fileExtension": "pdf",
        "fileName":      "rechnung.pdf"
      }
    }
  }
]
Wo liegen Binärdaten wirklich? Das ist ein Detail für später, du kannst es beim ersten Lesen überspringen. Die Base64-Kette oben ist nur die Sicht des Workflows auf die Datei. Wo n8n die Datei wirklich ablegt, regelt die Umgebungsvariable N8N_DEFAULT_BINARY_DATA_MODE. Seit n8n 2.0 landet sie nie mehr einfach im Arbeitsspeicher: im Normalbetrieb im Dateisystem, im Queue-Modus in der Datenbank, auf Wunsch in einem S3-kompatiblen Speicher. Der alte Wert default (Datei im Arbeitsspeicher) ist mit 2.0 weggefallen. Steht er noch in deiner .env-Datei, wirf ihn raus. Für dich ändert sich am Item nichts. Aber eine 80 MB große PDF-Datei bringt deine Instanz jetzt nicht mehr so leicht zum Absturz.

Wie Items in der Oberfläche aussehen

Öffne einen Node mit einem Doppelklick. Links siehst du das Eingangspanel (was ankommt), rechts das Ausgangspanel (was der Node ausgibt). In beiden Panels gibt es oben die Reiter Tabelle / JSON / Schema. Das sind drei Ansichten auf dieselben Items, nur anders dargestellt:

Tabelle zum Überblicken, JSON zum Verstehen, Schema zum Verdrahten

Beim Bauen hilft dir die Schema-Ansicht am meisten. Du siehst dort die Feldnamen und kannst sie per Drag-and-drop in ein Expression-Feld ziehen, statt sie abzutippen.

Ein Detail, über das viele stolpern: Tabelle und JSON zeigen alle Items, das Schema baut n8n dagegen nur aus dem ersten Item. Ein Feld, das erst im dritten Item auftaucht, fehlt dort. Wenn du ein Feld vermisst, schau zur Kontrolle in die JSON-Ansicht.

JSON in 3 Minuten (für alle, die unsicher sind)

Keine Sorge: JSON ist keine Programmiersprache. Es ist nur eine Schreibweise für strukturierte Daten. Du musst JSON nicht schreiben können, aber lesen. Es gibt genau diese Bausteine:

  Die JSON-Bausteine
{
  "text":    "in Anführungszeichen",   // String (Text)
  "zahl":    42,                  // Number
  "wahr":    true,                // Boolean (true/false)
  "leer":    null,                // nichts
  "liste":   [1, 2, 3],           // Array (geordnete Liste)
  "objekt":  {                       // verschachteltes Objekt
    "stadt": "Berlin"
  }
}

Das Wichtigste ist die Verschachtelung: Objekte können in Objekten stecken. Um an Berlin heranzukommen, schreibst du den Pfad mit Punkten: objekt.stadt. Lies das als „im Objekt objekt das Feld stadt“. Genau solche Pfade schreibst du gleich ständig.

Der Zugriff: Expressions & $json

Eine Expression ist ein kleines Stück Code in doppelten geschweiften Klammern: {{ … }}. Du schreibst sie in ein Eingabefeld eines Nodes. Beim Ausführen ersetzt n8n die Klammern samt Inhalt durch den echten Wert. Die wichtigste Variable darin ist $json, sie steht für die Daten des Items, das der Node gerade bearbeitet:

ExpressionBedeutung / Ergebnis
{{ $json.name }}Das Feld name des aktuellen Items → „Anna“
{{ $json.current.temperature_2m }}Verschachtelt: in current das Feld temperature_2m
{{ $json.liste[0] }}Das erste Element einer Liste (Zählung beginnt bei 0!)
{{ $json.alter + 1 }}Rechnen geht auch → 30
{{ $json.name.toUpperCase() }}Funktionen anwenden → „ANNA“
{{ $now }}Aktuelles Datum mit Uhrzeit, in der Zeitzone des Workflows
Woher weiß ich die Feldnamen? Aus dem Eingangspanel des Nodes (Schema-Ansicht). n8n zeigt dir dort genau die Felder, die gerade ankommen. Du musst nichts raten. Zieh die Felder per Drag-and-drop direkt ins Eingabefeld.

Auf andere Nodes zugreifen: $('Node-Name')

$json meint immer das json-Fach des Items, das gerade in den Node hineinläuft. Das ist also das Ergebnis des direkt vorherigen Nodes. Manchmal brauchst du aber einen Wert von weiter vorn in der Kette. Zum Beispiel die ursprüngliche E-Mail aus dem Trigger, obwohl schon drei Nodes dazwischenliegen. Dafür gibt es diese Schreibweise:

  Zugriff auf einen benannten Node
// Hol das Feld "email" aus dem Node namens "Webhook"
{{ $('Webhook').item.json.email }}

In die runden Klammern kommt der Name des Nodes, genau so geschrieben, wie er auf dem Canvas steht.

Die zwei Zugriffe, die du wirklich brauchst

$json.feld → Wert aus dem vorherigen Node.

$('Name').item.json.feld → Wert aus einem beliebigen früheren Node.

Mit diesen beiden verdrahtest du gefühlt jeden Workflow.

Ein Item oder viele? Das „läuft pro Item“-Prinzip

Hier kommt der häufigste Aha-Moment. Bekommt ein Node mehrere Items, führt er seine Aktion für jedes Item einzeln aus. Drei Items rein → Aktion läuft dreimal → drei Items raus. Du musst dafür nichts einstellen, das ist das normale Verhalten.

Es gibt Ausnahmen: Die Nodes Summarize, Aggregate und Merge fassen mehrere Items zu weniger Items zusammen. Alle anderen Nodes arbeiten die Liste einfach von oben nach unten durch. Was das Zusammenfassen für deine Expressions bedeutet, siehst du gleich im nächsten Abschnitt.

Du brauchst keine Schleife Willst du „für jede Zeile in der Tabelle eine Nachricht“, sorgst du dafür, dass jede Zeile ein eigenes Item ist. Den Rest macht n8n von allein, indem es den Node pro Item wiederholt. Kein for, kein Zähler.

Woher .item weiß, welches Item gemeint ist (Item-Linking)

Ein Node kann dieselbe Aktion 50-mal ausführen. Da stellt sich eine Frage: Welchen der 50 Webhook-Datensätze meint dann eigentlich $('Webhook').item? Antwort: genau den, aus dem das gerade bearbeitete Item entstanden ist. Dafür hängt n8n an jedes Ausgabe-Item eine unsichtbare Notiz: „Ich stamme aus Eingabe-Item Nummer X.“ Diese Notiz heißt paired item, das Verfahren heißt Item-Linking. Bei gleich vielen Ein- und Ausgabe-Items verknüpft n8n einfach der Reihe nach: Ausgabe 1 zu Eingabe 1, Ausgabe 2 zu Eingabe 2, und so fort.

Meistens läuft das automatisch, du merkst nichts davon. Du brauchst dieses Wissen erst an dem Tag, an dem eine Expression mit einer dieser beiden Meldungen abbricht. Beide haben eine klare Ursache:

MeldungUrsacheWas hilft
Multiple matching items for expression Mehrere Items wurden zu einem zusammengefasst, typisch nach Summarize, Aggregate oder Merge. Die Zuordnung ist nicht mehr eindeutig. Statt .item genauer werden: .first(), .last() oder .all()[0]. Oder einen anderen Node ansprechen, der denselben Wert eindeutig führt.
Info for expression missing from previous node Ein Node in der Kette liefert die Paarungs-Notiz gar nicht mit. Das passiert bei Code-Nodes, die Items selbst zusammenbauen, und bei manchen Community-Nodes. Im Code-Node die Paarung mitgeben (pairedItem). Bei fremden Nodes bleibt der Umweg über .first() oder .all(), weil beide ohne Paarungs-Notiz auskommen.

Daten „festpinnen“ zum Testen (Pinning)

Beim Entwickeln willst du nicht bei jedem Test echte E-Mails verschicken oder eine API hundertmal aufrufen. Die Lösung heißt Pin data (Daten anpinnen): Du führst einen Node einmal aus und pinnst sein Ergebnis fest. Bei allen weiteren Tests nimmt n8n diese gespeicherten Daten, statt neu abzurufen. Woran du es erkennst: Der angepinnte Node bekommt ein Pin-Symbol, und im Ausgangspanel steht das Banner „This data is pinned“. Willst du wieder frische Daten, klicke in diesem Banner auf „Unpin“.

1 Node ausführen → 2 im Ausgangspanel auf „Pin data“ klicken → 3 ab jetzt fixe Testdaten
Drei Grenzen, die du kennen solltest Erstens: Pinnen geht nur bei Nodes mit einem einzigen Hauptausgang. Zweitens: Enthält der Ausgang Binärdaten (Dateien), geht es gar nicht. Drittens: Gepinnte Daten gelten nur beim Entwickeln. Läuft der Workflow produktiv, ignoriert n8n sie und ruft die echte Quelle ab. Das ist gewollt, überrascht aber viele: Im Live-Betrieb tauchen die Testdaten plötzlich nicht mehr auf.

Wie das alles zusammenspielt: ein Durchlauf

So „denkt“ n8n, wenn du unten in der Mitte des Canvas auf „Execute workflow“ klickst (in älteren Versionen hieß der Knopf „Test workflow“):

  1. Trigger erzeugt das/die Start-Item(s)

    Beim manuellen Trigger ist das ein leeres Item, bei „Sheets lesen“ z. B. eine Zeile pro Item.

  2. Items wandern in den nächsten Node

    Der nimmt sie als Eingang (linkes Panel).

  3. Der Node arbeitet, Item für Item

    Er wendet seine Einstellungen an. Jetzt ersetzt n8n auch deine Expressions durch echte Werte.

  4. Er gibt neue Items aus

    Diese erscheinen im Ausgang (rechtes Panel) und sind der Eingang des nächsten Nodes.

  5. … und so weiter bis zum Ende

    Bis kein Node mehr folgt. Jeder Schritt ist in den Ausführungen nachvollziehbar.

Selbsttest: verstehst du den Kern?

  • Was ist der Unterschied zwischen $json und $('Trigger').item.json?
  • Du hast 5 Items im Eingang eines „Slack senden“-Nodes. Wie viele Nachrichten gehen raus?
  • Welche Ansicht (Tabelle/JSON/Schema) nutzt du, um die Feldnamen mit ihren Typen zu sehen? Und warum reicht sie nicht immer?
  • Wozu pinnst du Daten?
  • Warum kann $('Webhook').item hinter einem Merge-Node scheitern?
Antworten 1) $json = vorheriger Node, $('Trigger')… = ein bestimmter, beliebiger Node. · 2) Fünf, der Node läuft pro Item. · 3) Schema. Sie zeigt aber nur die Felder des ersten Items, für den vollen Datensatz musst du in JSON oder Tabelle schauen. · 4) Um beim Testen keine echten Aktionen auszulösen und APIs zu schonen. · 5) Merge fasst mehrere Eingabe-Items zu einem Ausgabe-Item zusammen, die Paarung ist dann nicht mehr eindeutig. Nimm .first(), .last() oder .all()[0].

Das mentale Modell steht. Spiel den Item-Linking-Fall am besten einmal selbst durch. Führe zwei Zweige über einen Merge-Node zusammen. Greif dann in einem Node dahinter mit {{ $('Webhook').item.json.email }} auf den Anfang zurück. Erscheint eine der beiden Meldungen aus der Tabelle oben, weißt du jetzt, woran es liegt. Im nächsten Kapitel gehen wir tiefer in Expressions: Datum berechnen, Texte zusammensetzen, Bedingungen prüfen. Damit bringst du Daten in genau die Form, die der nächste Node braucht.
